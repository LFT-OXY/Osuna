# Cross-model review report

The result of one cross-model review, as given to the user. Write it in the user's language — headings and labels too; only every reviewer's own answer stays in its original language. Call things by this skill's names: in Chinese the review is 「跨模型复查」, a reviewer 「复查员」, and 「复核」 means only a recheck (round 2 on) — never call a first review 「复核」. The parts come in this order, and a part with nothing in it is left out.

1. **Verdict** — one sentence. When no reviewer finished, the first sentence says this was not a cross-model review (in Chinese: 「这次没有做成跨模型复查」); nothing from you or a model of your family stands in for it. When some of the change went unread, the verdict says "partly unread" (in Chinese: 「有部分没看」).
2. **What was run** — the paragraph the user was told before the run: `notice` from `prepare`, copied whole and word for word in the user's language, also when what was said before the run came out shorter — never a summary of it. Around it add what it does not have. Together they give: the scope (base commit, number of files, lines) and the `snapshot` this review saved (a recheck starts from it; for a recheck also the snapshot it started from); each reviewer's tool, model and family when known, whether the family was only recognised by the model's name, and how many findings it raised; the files and reviewers left out, and why; whether a Codex reviewer read the user's personal instructions; that reviewers could read other files in the repository, read-only, and each got at most 30 minutes (in Chinese: 「最多 30 分钟」); how long it took — the time ATW measured, `durationMs` of the `run` output (each reviewer's own in its `result.durationMs`), not a time a tool or model claims; and the cost or usage as the channel handed it over, per reviewer: `result.costUsd` in US dollars, or else `result.usage` (token counts). When a tool reported no cost (`result.costUnreported` true and no `result.usage`), write "the tool reported no cost" (in Chinese: 「工具没报花费」). On a subscription account the review uses quota, not cash.
3. **The four tiers** — Must fix, Worth considering, Noted, Dismissed, each headed in the user's language: in Chinese 「要改」「值得考虑」「知道了」「驳回」, never the English names. A finding the spec does not settle goes into Worth considering marked "you decide" (in Chinese: 「要你定」), as [four-tiers.md](four-tiers.md) says. Each finding says which reviewer raised it, and findings raised by more than one reviewer are marked. Dismissed findings carry their reason. Write "all dismissed" when the four-tier rules call for it.
4. **Agreement and disagreement** — only with two or more reviewers: where they agree, and where they differ.
5. **Not read** — the parts any reviewer did not read, listed by file, and which reviewer left them; a reviewer that did not say what it left unread is named here too. When they add up to more than 500 lines, suggest folder groups to review separately.
6. **Reviewers that failed or did not finish** — which reviewer; where it stopped (never started, stopped partway, or finished without reading everything); its raw error, verbatim; whether the code had already been sent to it; whether any money was spent. A partial answer is marked "not finished" (in Chinese: 「没跑完」) and still given.
7. **Next steps** — the user may pick any findings, from any tier, to change; after changing them, the user may type the review command followed by 「复核」 (or `recheck`) to have the same reviewers check the fixes — give the exact text for the current tool only (Claude Code `/atw-cross-model-review 复核`, Codex `$atw-cross-model-review 复核`, pi and omp `/skill:atw-cross-model-review 复核`). From the third round on with Must fix still not empty, do not suggest a recheck; say it may be time to rethink.
8. **Each reviewer's answer** — in full, word for word, in its original language: its `result.text`, never translated or tidied.

A recheck uses the same parts, and states in the verdict which round it is; before the four tiers it marks each picked finding 「改好了」 (fixed), 「没改好」 (not fixed) or 「改了一半」 (half fixed), and its four tiers hold only new problems in the newly changed code.

When the change was reviewed in groups, it is still one report, with one section per group: parts 1, 2, 5 and 7 cover the whole change — part 2 names every group with its folders and line count — and parts 3, 4, 6 and 8 are given once per group, each under a heading that names the group's folders.

When the user picks findings to change, add the picked ones at the end of this report — through the script's `report --append`, so they are redacted too.

Before the report is shown or saved, the review script's `report` command redacts it: anything that looks like a secret, in your text or a reviewer's answer, becomes a placeholder naming its type, such as 「[已打码：私钥]」; nothing else changes. With a task the redacted report is saved under the task's `cross-model-review/` folder, one file per review named by date and time; with no task it is given in chat only.

A log review's report uses the same parts and is saved under the task's `log-review/` folder instead (`report --log-review`). Part 2 says what was read instead of a patch: the rows of the decision log and the runs they came from, the chat of each run, and how many places were redacted before sending. For a reviewer that was retried, the time and cost in part 2 are its `total` from the `run` output — every try added up, not the last one alone; when `total.costUnreported` is true, say that some tries reported no cost, so the cost given is only part of it. Part 5 lists each reviewer's `notRead.parts` word for word, not by file, with no folder groups — the reviewer names rows and stretches of the chat by their time; a reviewer whose `notRead` is null is named there too. Part 6 also lists every automatic retry: the reviewer, the cause of each try (`reason`) and how it ended, and a retry left out because the 30 minutes were nearly used up (`retryStoppedBy`). There is no recheck, so part 7 offers only picking findings. So that `decision_log.py pending` can list the Must fix findings still open, put Must fix under a heading of its own (`## 要改`, in English `## Must fix`) with each finding as `### N. <title>`. When the user handles one — picks it to change, or decides it needs no change — append, through `report --append`, a section `## 已处理` (in English `## Handled`) with one line per finding: `- 要改 N：<reply>` (in English `- Must fix N: <reply>`).
