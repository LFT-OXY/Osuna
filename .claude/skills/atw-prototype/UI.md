# 界面原型

界面原型分两段：

- **第一段：选方向。** 先认品类、拆标杆，用文字写出三个风格和结构都明显不同的方向请用户选；用户想看实际画面时，再把三个方向各做成一张首屏放进同一个对比页挑，并说出具体喜欢和不喜欢哪里。
- **第二段：深化成可交互原型。** 只在问题包含“用起来对不对”时才做：把选定方向做成完整页面，接上按 [LOGIC.md](LOGIC.md) 写的纯逻辑模块，让人能把真实业务流程完整点一遍。

两段的产物都是用来做决定的，不是正式代码。选定之后的正式界面由 atw-ui 按设计说明重新实现。

如果问题只关于逻辑或状态、与外观无关，分支选错了，改用 [LOGIC.md](LOGIC.md)。

## 什么时候用

- “这个页面应该长什么样？”
- “正式做之前，我想先看看这个后台有几种可能。”
- “给设置页换个布局试试。”
- “这个下单流程连同规则，用起来顺不顺？”（两段都做）
- 任何用户本来要在脑子里对着三张模糊草图纠结一整天的时候。

## 承载方式：优先挂在已有页面上

要做出画面时才选承载方式：第一段的三个首屏，或第二段的完整页面。用户从文字里就选定了方向、又不做第二段时，不建任何页面。

界面原型**贴着应用的其他部分**才好判断：真实的顶栏、侧栏、数据和密度。一个孤零零的新页面是真空，每个方案单独看都还行。所以只要有合理的宿主页面，就优先方式 A。

### 方式 A：在已有页面上调整（优先）

路由已经存在。各方案**在同一路由上**渲染，用 URL 参数 `?variant=` 切换。现有的数据获取、参数和权限都保留，只换渲染部分。

还没有页面、但*自然属于某个页面*的东西（后台里的新区块、设置页里的新卡片、现有流程中的新一步）也算方式 A：把方案挂在宿主页面里。

这些方案同时放进对比页作为本机地址候选（`"kind": "url"`），并把当前页面作为基线（`"baseline": true`），每个方向都和现状对照。见 [风格对比页](references/style-explorer.md)。

### 方式 B：独立小样（没有宿主页面时）

只有确实没有可挂靠的页面时才用，例如全新的顶层界面、或嵌不进任何现有位置的流程。先确认：真的没有现有页面能挂吗？空页面会掩盖有数据时才暴露的设计问题。

方式 B 默认做成自包含的单个 HTML 小样，直接放进对比页，双击就能打开，不需要服务器。小样必须用到项目里的组件或框架时，按项目已有的路由约定建一个一次性路由，名字里带 `prototype`，同样用 `?variant=` 切换，并作为本机地址候选放进对比页。

## 第一段：选方向

### 1. 写下问题，定方向数量

默认写 **3 个方向**。用户要更多时照做，但超过 5 个就不再是“明显不同”而是噪音，上限 5。窄小的任务不强求多方案；任务明确只要一个方向时只写一个，见第 6 步。

把计划写成一句话；做出画面时放在原型所在位置或文件顶部注释里：

> “设置页的三个方向，先用文字问；要看画面时用 `?variant=` 在现有 `/settings` 路由上切换，并汇总到对比页。”

用户在不在场都适用。

### 2. 认品类，拆标杆，写方向卡

方向未定时按 [设计方向](references/design-direction.md) 的顺序做：先认品类、拆标杆，标杆的真实画面存进 ATW 任务目录的 `references/`（没有任务时放在原型旁边），不写进技能安装目录；再从产品题材、受众和使用场合推出调性；每个方向从一个具体的生成引擎出发，色彩按“定色彩”的四步从产品推出；写文案之前先定首屏骨架，说服型页面按 [说服型页面首屏骨架](references/direction-persuasion.md) 选，内容和工作区页面的首屏就是第一排内容；为每个方向填方向卡，最后逐条做差异检验。

这一轮几个方向共用调性和标杆与取舍，每个方向只填北极星、生成引擎、首屏骨架、字体、色彩、主视觉、图标和控件语法；其余各栏在方向选定后补齐，见第 7 步。

方向**必须在结构上不同**：布局、信息层级、主要操作方式都不一样，不只是换颜色。三个微调过的卡片网格不是界面原型，是墙纸。两个方向太像时，回到骨架重选其中一个，不靠换装饰补救。

方向由用户的品味来定，不直接采用模型自己想出的方向。任务目录里已有 `ui-direction.md`，或用户明确指定了一个完整的方向时，跳过第一段，直接进入第二段或交给 atw-ui。用户只给了参考图、品牌规范或说了想要的风格，不算给定方向：仍写三个方向、走第 3 步，三个方向怎样写见第 6 步。

### 3. 先用文字问一次

方向卡写完，不急着做页面。把每个方向用三四行写给用户：它给人什么感觉，首屏长什么样，用什么字体和色彩，主视觉靠什么。附上你推荐哪一个和理由，然后问：按其中一个定下来，还是把三个都做成首屏放在一起比。发给用户后这一轮结束。

- 用户选了一个，或者从描述里已经说清想要什么：方向就定了，定下的就是这一个方向。第一段不做首屏，也不做对比页：按 [设计方向](references/design-direction.md) 的“差异检验”把它和拆过的标杆并排比一次，确认不撞脸，然后到第 7 步补齐方向卡、写设计说明。完整页面在第二段或 atw-ui 里做。
- 用户想看实际画面：按第 4 步把三个都做成首屏。
- 之后凡是要做出几个候选让用户挑，都先这样用文字问一次：用户从文字里定得下来，就定选中的那一个，不把几个候选都做成画面。

### 4. 用户要看实际画面时，做三个首屏

每个方向都是一张真实的首屏，骨架、字体、色彩和主视觉都拉开。只做看得出风格所需的东西：

- 每个方向一个文件（方式 A 是一个方向组件，导出清楚的组件名，例如 `VariantA`、`VariantB`、`VariantC`；方式 B 是一个 HTML）、一个视口、只有主状态；不写交互，不做响应式和动效，不取证，不派评审。
- 几个方向共用同一份示例文字和数据，只写一次；页面的用途、核心内容和主要操作也相同。结构和样式各写各的：不用同一个模板换几组样式来生成，那样几个方向的骨架天生是同一个。
- 方式 A 用项目已有的组件库和样式体系（TailwindCSS、shadcn、MUI、纯 CSS 等）；方式 B 的独立首屏不受此限，但图标只内联用到的 SVG，不引用外部资源。
- 主视觉靠图的方向，生成一张，至多重新生成一次；其余图位先用从页面取色的色块占着。
- 每个方向用宿主的浏览器工具截一张图自己看过，改掉重叠、裁切和明显的粗糙就交。

首屏选能暴露方向优缺点的那一页：含复杂表单的产品不能只做封面。示例内容按真实产品的样子写，避免整数指标和“标题”“描述”这类占位字；画面上不出现“示例”“示意图”“按钮未接入”这类制作说明，这些写进交付说明。视觉层级、字体、色彩和留白的判断见 [视觉语言](../atw-ui/references/visual-language.md)。

按 [风格对比页](references/style-explorer.md) 准备 `manifest.json`，把方向卡里的北极星、字体、色板和特征写进去，用内置生成器组装成一个离线 HTML。不要每次自己重做对比工具。对比页和 manifest 放在 ATW 任务目录（没有任务时放在原型旁边），不写进技能安装目录。

### 5. 交对比页，版式也先用文字问

把对比页交给用户，这一轮到此结束：附上推荐理由，请用户选一个方向、说出具体喜欢和不喜欢哪里，并说明想比较不同的版式也可以说。用户只说“再高级一点”这类模糊词时，用设计方向里的翻译表追问，或拿两张首屏让用户比较。三个首屏和版式变体不派评审；用户明确要求时，才按 atw-ui 的 [视觉评审派发协议](../atw-ui/references/visual-review.md) 评一轮。协议里说的“本 Skill 目录”是 atw-ui 的目录：给评审者的是 [评审手册](../atw-ui/references/reviewer-manual.md) 的绝对路径。首屏没跑截图工具，没有 `report.json`，不交默认做法提示，交接里写明未跑截图工具。

用户要比版式，先用文字写出两三种骨架的差别；从文字里定得下来就按选中的定，要看实际画面再做成首屏，连同选中的那一版放进对比页再选一次。版式之间保持选定方向的字体、色彩和控件语法，只在骨架、主视觉的摆法和页面结构上拉开。用户只回了选哪个，就把意见并进去，到第 7 步；想把两个方向拼在一起的，先做出拼合后的首屏给用户确认。

### 6. 哪些情况不这样走

- 只要设计说明时不做页面，用文字写下方向的决定。
- 用户已经给了参考图、品牌规范或说清了风格，风格就定了：三个方向都留在这个风格里，只在骨架、主视觉和页面结构上拉开。
- 用户说了“你定”“直接做”，或者无人值守时，不问：三个首屏仍做出来放进对比页留档，把三张截图缩到 480px 宽并排看一次，自己选定并写明理由，接着到第 7 步。
- 任务明确只要一个方向时不问也不做对比页，直接写方向卡，再按 [设计方向](references/design-direction.md) 的“差异检验”把它和拆过的标杆并排比一次，确认不撞脸。

### 7. 写设计说明

方向选定后先把方向卡补齐：第 2 步没填的页面结构、各区块的形式、动效、结构性突破、记忆点和放弃什么都填上，“标杆与取舍”里写明标杆画面的存放路径。

再写一份简短的**设计说明**：用户任务、内容与主动作、选定方向（附补齐后的方向卡，标杆与取舍、各区块的形式、控件语法和动效四栏都在）、用户的喜欢与不喜欢、视觉关系、关键状态、设备约束和验收重点。放在 ATW 任务目录的 `ui-direction.md`；已有说明直接更新。这份说明是第二段和 atw-ui 的依据。

## 第二段：深化成可交互原型

只有问题包含业务规则或完整操作流程时才做；只问外观时，第一段选定后就收尾。

### 1. 先写逻辑模块

按 [LOGIC.md](LOGIC.md) 第 2 步，把业务规则写成一个纯模块（reducer、状态机或纯函数），不碰 DOM。这部分以后能整体搬进正式代码，是第二段最值得保留的产物。

### 2. 选定方向做成完整页面

把选定方向做成完整页面（做过首屏的从首屏扩展），作为逻辑模块外面的一层外壳：页面只调用模块、渲染模块返回的状态。关键状态都要在界面上有样子——空、加载、成功、失败、被拒绝的非法操作——不只做漂亮的默认状态。

方向卡里的记忆点（某个动作的反馈、完成的那一刻）在这里做出来；动效遵循方向的调性。修改数据的动作一律经过逻辑模块，接口用桩代替，不接真实后端。

默认只深化**一个**选定方向。用户要求同时比较两三个方向的完整体验时，多个外壳共用同一个逻辑模块，逻辑只写一次。

### 3. 加一个状态抽屉

LOGIC.md 里的“当前状态面板”和“引导演练”放进一个可开关的抽屉，供不写代码的人逐步走查业务规则：

- 抽屉视觉上明显不属于设计本身（例如高对比的面板），和浮动切换条一样，不参与设计评判。
- 抽屉里保持朴素：标签式的状态字段、标出刚变化的部分、按场景划分的演练按钮；不加动画。
- 开始演练时重置到已知初始状态。
- 生产构建中隐藏。

### 4. 承载

- **没有现成项目**：单个 HTML，脚本内联，双击即可打开；放进对比页时加 `"interactive": true`，单张查看时就能直接操作。
- **有现成项目**：挂在已有页面上，用 `?variant=` 切换；作为本机地址候选放进对比页。

## 接线（方式 A）

在路由上建一个切换组件：

```tsx
// 伪代码——按项目框架改写
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

已有页面：现有数据获取都放在切换组件之上，各方向只替换渲染的子树。一次性路由：同一个切换组件挂在 `prototype` 路由下。

## 浮动切换条（方式 A）

屏幕底部居中、固定位置的小条，三部分：

- **左箭头**：切到上一个方向（循环）。
- **方向标签**：当前方向的编号，方向有名字时一并显示，例如 `B — 侧栏布局`。
- **右箭头**：切到下一个方向（循环）。

行为：

- 点箭头时用框架的路由更新 URL 参数（Next 用 `router.replace`，React Router 用 `navigate` 等），保证方向可分享、刷新不丢。
- 键盘 `←` `→` 也能切换。焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 上时不拦截方向键。
- 视觉上明显区别于页面（例如高对比胶囊、轻阴影），一看就不属于被评判的设计。
- 生产构建中隐藏——用 `process.env.NODE_ENV !== 'production'` 或等价判断，避免误合并后把切换条发给用户。

切换条做成一个共享组件，放在项目存放共享界面组件的位置。对比页适合并排比较；切换条适合在真实页面里来回看，开发服务器禁止被嵌入时也只能靠它。

## 交给用户

做了画面时，给出对比页路径、页面地址和 `?variant=` 的取值；第二段还要说明状态抽屉怎么打开、有哪些演练场景。用户有空时会翻看。最有价值的反馈常常是 **“我要 B 的顶栏配 C 的侧栏”**——那才是他们真正想要的设计。

交付说明里写清：哪些是模拟数据、生成图片、未接入的动作；实际查看过哪些视口；哪一步没做以及原因。

## 记录结论，收起原型

用户选定后，先记录结论——选了哪个方向、为什么、用户的喜欢与不喜欢——更新到 `ui-direction.md`，并把影响需求的部分写进任务的需求文档。然后按 [SKILL](SKILL.md) 的规则收起原型。所有方向、切换组件、对比页和 manifest 进入一次性分支，作为一手资料保存，不进主分支：

- **方式 A**：主分支上去掉所有方向和切换条，现有页面保持原样。
- **方式 B**：主分支上去掉一次性路由和切换条。
- **第二段**：验证过的逻辑模块搬进正式代码；页面外壳留在一次性分支。

正式界面交给 atw-ui，按 `ui-direction.md` 在正式代码里重新实现。留在主分支的方向组件和切换条很快会腐烂，还会误导下一个读代码的人。

## 反模式

- **不问就做三个首屏。** 用户在场时先用文字问一次；从文字里定得下来，就不做首屏和对比页。
- **方向之间只差颜色或文案。** 那是微调，不是原型。真正的方向在结构上互不相同。
- **按明暗分方向。** “一个亮、一个暗、一个暖”是最常见的失败；每个方向要有自己的色彩身份。
- **默认左右分栏。** 一轮里最多一个方向用左右分栏，并写出为什么非它不可。
- **方向之间共享太多代码。** 共享 `<Header>` 可以；共享 `<Layout>` 就失去意义了。每个方向都应该能推翻布局。
- **把方向接到真实的写操作上。** 只读原型没问题；需要修改数据时经过逻辑模块、指向桩。问题是“它应该长什么样、用起来对不对”，不是“后端通不通”。
- **把业务逻辑写进页面事件里。** 第二段的规则必须在纯模块里，否则既不能搬走，也没法在状态抽屉里走查。
- **把原型直接提升为正式代码。** 原型代码是在原型约束下写的（没有测试、错误处理很少）。正式实现交给 atw-ui 和实现阶段重新写。
