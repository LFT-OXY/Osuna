# Quality Guidelines

`docs/coding-standards.md` is the rulebook. Reviewers apply all of it. This file lists the daemon-specific checks and the commands that prove them.

## Daemon-specific rules

- **The density sweep in [the app checklist](../../app/frontend/quality-guidelines.md#checks-reviewers-run) applies here too.** Review applies `docs/coding-standards.md` §Density to daemon code and tests the same way.
- **Validate at the boundary, then trust the type.** Boundaries here are the WebSocket (zod-aot generated validation), `$PASEO_HOME` files (Zod in the store), process output (`utils/run-git-command.ts`, `utils/tool-call-parsers.ts`), and plugin/MCP inputs. Past those, no `?.`, no `??`, no re-checking.
- **Spawn through `utils/spawn.ts`; run Git through `utils/run-git-command.ts`.** Git is scheduled by `utils/git-process-scheduler.ts` under the limits in daemon config (`docs/data-model.md` "Git process limits") and traced by `utils/git-command-trace.ts`. A raw `child_process.spawn("git", …)` bypasses all of that.
- **Checkout diff: tracked and untracked files follow one budget rule.** `utils/checkout-git.ts` reads both in batches of `TRACKED_DIFF_BATCH_SIZE` with `Promise.all` and relies on the git scheduler for concurrency (no second pool); results are appended in the original order so output stays deterministic. The 2MB `TOTAL_DIFF_MAX_BYTES` budget is decided per file: a file that does not fit gets `status: "too_large"` and later smaller files still show; never `break` and drop the rest. Once the budget is used up, skip `git diff` but still sniff binary (`inspectUntrackedFile`), so a binary file is `binary` no matter which batch it lands in. Concurrency did not shorten refresh in the diff-panel scenario: ~60 git processes per refresh already queue on the 64/s rate limit, and highlighting is ~87% of refresh time (10-19-diff-view-large-changesets 03, `research/baseline.md`). Tests: `checkout-git.test.ts` (untracked overflow → `too_large`, concurrent = serial, budget-exhausted binary → `binary`).
- **`CheckoutDiffManager` pushes one target at most once a second.** After the 150ms debounce, refreshes of a target start at least `CHECKOUT_DIFF_MIN_PUSH_INTERVAL_MS` (1s) apart, and a push that would land within 1s of the previous one waits on `target.pushGapWait` (cleared in `closeTarget`, so no timer survives an unsubscribe). The trailing push lands at the later of "last change + 150ms" and "last push + 1s" — the 1s gap wins (user decision, 10-19-diff-view-large-changesets 04). During that wait `latestPayload` and `latestFingerprint` stay on the previous result and are swapped together at push time; updating only `latestPayload` gives a new subscriber the new result and then pushes it again. A change arriving while computing still queues exactly one refresh. Tests: `checkout-diff-manager.test.ts` (exact push times under 5s of changes, queued-once refresh, no timer after release, no duplicate push to a subscriber who joined during the wait).
- **Checkout diff reuses work per file; identity, not the watcher, decides.** `utils/checkout-diff-file-reuse.ts` caches each file's patch and highlight per `CheckoutDiffManager` target, passed in as `readOptions.fileReuse` to `getCheckoutDiff`; one-off reads pass none and never reuse. Identity = compare params (incl. `ignoreWhitespace`) + path + status/oldPath + old-side blob + new side (worktree `lstat` size/mtimeNs/ino/mode, symlink target too; in base mode the target commit's blob). Watcher paths (`{ changedPaths }`) only add invalidation hints; a signal without paths falls back to identity, so polling and base mode stay correct. Never reuse gitlinks (mode 160000) or untracked directories: their own stat does not change when the submodule or its contents do. Each path's cached value is read once per run and frozen until the run ends, or a watcher hint mid-run makes a highlighted file rebuild without its full-file contents. The 2MB budget, `too_large` and `binary` are re-decided every run from the cached raw patch bytes; only highlights of non-placeholder files are reused. The per-file cache lives and dies with the subscription (`closeTarget` clears it; files that left the change list are dropped each run); it is deliberately not cleared by `invalidateCheckoutDiffCache`, or nothing would ever be reused. stat errors: ENOENT/ENOTDIR/ELOOP → absent, EACCES/EPERM → not reusable, anything else throws. Result for a one-file change in the diff-panel scenario: 9.0s → 0.27s (10-19-diff-view-large-changesets 05). Tests: `checkout-diff-file-reuse.test.ts` (tracked/untracked/delete/rename/ignoreWhitespace/no-path signal/base mode equal a from-scratch run; mid-run hint; submodule).
- **Checkout diff marks generated files on every run, outside the per-file reuse.** `utils/generated-files.ts` `findGeneratedPaths({ cwd, paths, runGitCommand, logger })` asks one `git check-attr -z --stdin linguist-generated` for all changed paths (never one process per file). An explicit `linguist-generated` true/false in `.gitattributes` wins, including false over the lock list and the `*.min.js` / `*.min.css` / `*.map` suffixes (GitHub linguist behaviour); otherwise the orca-derived lock list and suffixes decide (renamed files by new path, deleted files too). The flag is sent as optional `generated: true` only, never `false`, and is not stored in the per-file reuse cache, so a `.gitattributes` edit takes effect on the next run. It only drives default collapse: a failed or truncated `check-attr` logs a warning and falls back to name rules instead of failing the diff. `check-attr` reads the worktree/index attributes even in base mode. Tests: `checkout-git.test.ts` (lock files, min/map, `=true`, `=false`, rename, delete, check-attr failure), `checkout-diff-file-reuse.test.ts` (`.gitattributes` edit under reuse), `checkout-diff-subscription.e2e.test.ts`, `messages.wire-compat.test.ts` (both directions).
- **Path handling goes through `utils/path.ts`** (`createRealpathAwarePathMatcher`, normalization) and `server/path-utils.ts`. Workspace ids are opaque; never derive a path from one.
- **Kill process trees**, not processes: `utils/tree-kill.ts`.
- **Long-lived watchers have owners and teardown invariants.** Read `docs/file-observation.md` before adding a recursive watcher; `server/watcher-liveness-canary.ts` exists because teardown bugs were real.
- **Terminal and agent stream paths are performance-sensitive.** `docs/terminal-performance.md` and `docs/agent-stream-performance.md` name the coalescing and backpressure invariants; do not add per-chunk work there without reading them.
- **Executable lookup uses `executable-resolution/`**, including the Windows variant. Do not shell out to `which` from a feature.
- **Provider directories follow the upstream CLI's own rules.** Resolve a provider's config and session directories from the variables that CLI itself reads — `providers/omp/provider-config.ts` (`resolveOmpRoots` / `resolveOmpSessionPaths`, used by the Usage log roots and diagnostics) mirrors OMP's `pi-utils/dirs.ts`, and session import resolves the same rules through upstream's `resolveOmpSessionsDir` in `providers/omp/session-descriptor.ts`; a rule change goes into both until they are one — and read them from `{ ...process.env, ...runtimeSettings.env }` so a launched agent and a directory scan agree on the path. Never invent a Paseo-only variable: `OMP_AGENT_DIR` and `OMP_SESSION_DIR` existed nowhere upstream, so a user who configured OMP correctly still got an empty session list. Codex: a session gets `codexHome` from `resolveCodexHomeDir(buildCodexAppServerEnv(runtimeSettings, launchEnv))`, and `CodexAppServerAgentClient.discoverCommands` resolves it the same way without `launchEnv`; never read `process.env.CODEX_HOME` directly, or a custom provider's draft `/` menu lists the daemon home's prompts (test: `codex-app-server-agent.test.ts` "discovers prompts and skills from the CODEX_HOME a custom provider runs Codex with").
- **A runtime provider param must not default to a literal that shadows its own fallbacks.** `sessionDir: params.sessionDir ?? "~/.omp/agent/sessions"` left every later branch — project `settings.json`, the upstream-derived directory — permanently unreachable, and the dead branches still typechecked and still had tests. Leave the param `undefined` when unset and let the resolution chain run.
- **A provider adapter maps a native message once, for both live and history replay.** Visibility and display-text rules live in one exported function that the live handler and the history mapper both call — `shouldDisplayPiCustomMessage` and `restorePiSkillCommand` in `providers/pi/history-mapper.ts`, `shouldDisplayOmpCustomMessage` in `providers/omp/custom-message.ts`. Honor what the upstream message declares (`display: false`), never the content's tags (`<workflow-state>`, `customType: "atw-runtime-context"`). Pi's adapter mapped every custom message to `assistant_message` on both paths, so an extension's hidden runtime context flooded every turn. Hiding a row must leave the turn lifecycle untouched. Test both seams: `pi/agent.test.ts` and `pi/history-mapper.test.ts`. `docs/providers.md` has the Pi/OMP contract.
- **A model's `thinkingOptions` list only the levels the upstream provider accepts for that model, and the session reports the level the provider actually applied.** Derive options from the upstream per-model metadata with the upstream's own rule (Pi: `thinkingLevelMap`, in `resolvePiThinkingConfig` in `providers/pi/agent.ts`; OMP: `model.thinking.efforts`). A reasoning model whose levels are all mapped to `null` gets no options, the same as a non-reasoning model. `AgentManager.setAgentThinkingOption` calls `session.getRuntimeInfo()` after the session returns and stores the level it reports, so `getRuntimeInfo` must return the applied level; a read that throws there fails the set and keeps the previous level. `setAgentModel` does not read runtime info. It learns about a level change only through `thinking_option_changed`, which survives because it drains session events. So when the provider changes the level on its own, as Pi's `set_model` does by resetting to its settings default, re-apply the level from before the switch, read back the applied one, and emit `thinking_option_changed` if the reported level changed, including when the re-apply fails and the level stays at the provider's reset value. Pi keeps the level to re-apply in `selectedThinkingLevel`. On a model with no levels Pi reports `off`; that value must not overwrite it, and the session keeps reporting the remembered level until a model with levels is current again. Inside the Pi session a failed `get_state` after `set_thinking_level` or `set_model` logs a warning and records the requested level or the returned model. Upstream Paseo throws in both places; Osuna keeps the operation successful (maintainer decision, 2026-10-10). Claude's `reconcileThinkingOptionForModel` follows the same pattern. Tests: `pi/agent.test.ts` ("reports the clamped thinking level when switching…", "restores the thinking level after passing through a non-reasoning model", "reports the level Pi reset to when re-applying the thinking level fails", "completes a model switch when reading Pi state back fails", "exposes only the thinking levels each model's thinkingLevelMap supports").
- **A Claude model's default thinking level comes from its manifest entry, not from the global constant.** `ClaudeModelManifestEntry.defaultThinkingOptionId` is optional and `getDefaultThinkingOptionId(model)` in `providers/claude/model-manifest.ts` falls back to `CLAUDE_DEFAULT_THINKING_OPTION_ID` (`high`). The `isDefault` option, `AgentModelDefinition.defaultThinkingOptionId`, and `resolveClaudeDisabledThinkingForModel(...).fallbackThinkingOptionId` all read it, so new code that needs a model's default calls the helper and never compares against the constant. Opus 5.5 sets `medium`, following upstream #5200 (maintainer decision, 2026-10-10; Osuna's own entry defaulted to `high` before the v0.9.1 merge). `getClaudeCustomModelThinkingOptions` still uses the constant because custom models have no manifest entry. The file is kept byte-identical to upstream: Osuna-only behaviour is pinned by tests appended as their own `it` in `models.test.ts` ("resolves provider-prefixed Opus 5.5 IDs to the catalog entry"), not by edits to the manifest. Tests: `models.test.ts` ("offers every effort level except off, because Opus 5.5 cannot disable thinking", "resolves disabled thinking for model %s").
- **Never type a control byte into source; write the escape.** A `\0` separator entered as a raw byte makes the file binary to Git: the diff renders as `GIT binary patch`, so the whole file lands unreviewed, and blame and merge degrade. Write `"\u0000"`. `rg -l $'\x00' -- '*.ts'` finds any that slipped in.
- **`session.ts`'s dispatch chain, `bootstrap.ts`'s `createPaseoDaemon`, the `AgentManager` constructor, and the `VoiceAssistantWebSocketServer` constructor in `websocket-server.ts` all sit at the `eslint(complexity)` ceiling of 20.** One more `??` link in the chain, or one more `?.`/`??` inside `createPaseoDaemon`, fails lint. Put a new RPC in an existing domain dispatcher, and push option defaulting into the service's own constructor or a module-level factory rather than into the bootstrap expression.
- **`bootstrap.ts` must not contain a provider id, not even in a comment.** `terminal/agent-hooks/claude/claude.test.ts` lowercases the whole file and fails on any key of `AGENT_HOOK_PROVIDERS` (`claude`, `codex`, `opencode`). Wire services with provider-generic callbacks, e.g. `providerRuntimeSettings: (provider) => providerSnapshotManager.getRuntimeSettings(provider)`, and let the service name the provider it needs. Local runs of only the changed test files miss this; it surfaces in CI `server-tests`.
- **A new optional `AgentClient` or `AgentSession` method must be forwarded by hand in `agent/provider-registry.ts`.** `wrapSessionProvider` copies methods one by one; `wrapClientProvider` takes Osuna's optional client methods (`discoverCommands`, `resolveInstalledVersion`, `resolveCliLaunch`) from `forwardOsunaClientMethods(inner)`, so a new one is added there and upstream's lines in `wrapClientProvider` stay untouched (the function sits at the lint complexity limit). Every profile that extends a built-in (`zai` extends `claude`) or overrides models goes through them. A missing line typechecks and silently drops the capability for those users only. `provider-registry-wrap.test.ts` enforces this for session methods at the type level; client methods have no such check, so add a case to `provider-registry.test.ts` (see "wrapped claude profile keeps no-process command discovery"). `mcp-parity.e2e.test.ts` builds its own wrapper and needs the same line.
- **A client that picks between implementations forwards the same optional methods.** `providers/opencode/runtime-client.ts` (`OpenCodeRuntimeClient`) is what the registry builds for `opencode`; it chooses the 1.x or 2.x client after probing `opencode --version`. It forwards `discoverCommands`, `resolveInstalledVersion`, and `resolveCliLaunch` to the 1.x client without probing: the first must not start a process (ADR 0003), and the other two depend only on the configured command. It has no client-level `listCommands(config)`; `AgentClient` has none. Test: `runtime-client.test.ts` "serves static commands, installed version and CLI launch without selecting a runtime".
- **Listing commands never starts a provider process.** `AgentSession.listCommands` answers only from a process that is already running and returns `null` otherwise, including before that process has reported a list (an empty placeholder would overwrite the cached one); `AgentClient.discoverCommands` scans directories and returns built-ins without running git or any other process. Never call a lazy "ensure the process" helper (Claude's `ensureQuery`, Codex's reconnect, OpenCode 1.x's `reconnectIfServerExited`, the OpenCode 2.x session's `reconnectIfExited`) from either. Upstream's own `listCommands` calls these helpers, so a provider path taken from upstream as-is needs this checked by hand; `opencode/v2/session.ts` returns `null` once its helper server has exited or the session is closed (test: `opencode/v2/agent.test.ts` "lists commands only from the helper the session already holds"). A session publishes each full list its process reports as a `commands_changed` stream event; `AgentManager.dispatchSessionEvent` records it in the catalog (test: `agent-manager.test.ts` "a session's command report fills the catalog…"). Contract: `docs/providers.md`; rule: `docs/adr/0003-command-list-never-spawns.md`.
- **Code or content taken from another project carries a header and an entry in the root `THIRD_PARTY_NOTICES`.** This holds in every package (the app's model families and vendor icons too). A ported file starts with two comment lines: what was ported from where (repo URL and source files), then `Copyright (c) <year> <holder>. MIT License — 完整声明见本仓库 THIRD_PARTY_NOTICES。` (see `api-endpoints/gateway/failure.ts`). A verbatim copy under another license says so the same way (`api-endpoints/codex-base-instructions.ts`, Apache-2.0). A test that reuses the other project's cases or quoted vendor texts names the source and the file in its header comment (`magpie（MIT，THIRD_PARTY_NOTICES）`, as in `gateway/translation/chat.test.ts`). Every one of these files is listed by path under its project's section in `THIRD_PARTY_NOTICES`, and the full license text is there (Apache-2.0 points at the root `LICENSE`). Check before committing: every file that `rg -l -i "magpie|openai/codex" packages --glob '!**/node_modules/**'` finds as a source or reused test is in the notices file. API endpoint ticket 13 found `gateway.ts`, three gateway tests, `model-families.test.ts`, and the Codex instructions missing.
- **Bash scripts start with `#!/usr/bin/env bash`.**
- **`function` declarations, `interface` over `type`, no barrels, no `any`, no `as` to silence errors, no `@ts-ignore`.** The TypeScript config is strict and `typecheck` runs `tsgo` on `tsconfig.server.typecheck.json`.
- **Object parameters** for 3+ args, any boolean, or any optional argument. `createPaseoDaemon(config, logger)` and store constructors already follow this.

## Forbidden

- `console.log` / `console.error` outside entrypoints.
- `process.exit` from a feature module.
- A new flat RPC name, or a `.request` without `.response`.
- Untagged back-compat. Every shim carries `// COMPAT(name): added in vX, remove after <date>`.
- Restarting the daemon on port 6767 without permission.
- `npm run test` for the whole workspace.
- Adding auth checks or env gates to tests.
- Hand-written types that duplicate a Zod schema or a protocol type.
- `-utils` / `-helpers` / `-manager` suffixes on new files.

## Verification after every change

```bash
npm run typecheck
npm run lint
npx vitest run <the file you changed> --bail=1
npm run format          # before committing
```

If `typecheck` fails in a package that depends on another workspace, rebuild first (`npm run build:server`) instead of patching declarations. Lint is oxlint with `correctness`, `suspicious`, and `perf` categories as errors plus `no-shadow`, `preserve-caught-error`, `promise/always-return` (`.oxlintrc.json`); fix the code, do not disable the rule.

## Before opening a PR

`docs/qa.md` sets the evidence bar: the commands you ran and their output, a regression test that fails on the broken version for any bug fix, and the platforms you could not test. `CONTRIBUTING.md` explains why PRs without this are closed.
