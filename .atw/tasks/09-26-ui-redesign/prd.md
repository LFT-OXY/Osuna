# UI 重设计（以 t3code 为主参考）

## 问题陈述

Osuna 的界面沿用上游 Paseo 的视觉。用户更喜欢 t3code（以及 multica、orca）那种高密度、中性灰加单一蓝色强调、靠底色明度分层的桌面工具风格，想把整套 UI 重新设计一遍，但不知道从哪儿改、改哪些，也担心一次性大改无法回退。

代码现状：颜色、间距、字号、圆角基本已经 token 化，换皮本身便宜。但文字、行、卡片这些排版样式没有统一的基础组件，分散在约 278 个组件文件各自的样式表里，想让整体观感一致，就得逐个文件改。现有 20 套主题共用两个 builder，新增语义角色意味着每套主题都要补值。项目已不再合并上游，布局可以动，但用户选择保留现有的工作区结构。

## 解决方案

以 t3code 为主参考、multica 为补充，按三个阶段渐进重设计，每个阶段都能单独验证和回滚：

1. **token 与主题**：引入新的语义 token 结构，新的亮色和暗色成为默认主题；其余主题（含插件主题）缺少的新角色用公式从原有颜色派生，不逐套手调。毛玻璃和噪点质感只在 Web 和 Electron 上开启，原生端降级为纯色。
2. **基础组件**：补齐用途命名的文字组件（Text）和行组件（Row），并把现有控件（按钮、菜单、输入、浮层、sheet）的外观对齐新 token。
3. **逐页迁移**：左侧栏、工作区 tab 条与 pane 头、对话流、Composer、Explorer sidebar 与 diff、设置页、菜单和对话框，逐个迁到新组件和新 token。

布局结构不变：保留左侧栏（项目 → 工作区）、工作区多 tab 与分屏、右侧 Explorer sidebar。验收以 Electron 桌面端为主，移动端跟随 token 变化，不单独设计。视觉基准是本任务的原型（见"补充说明"）。

## 实现决策

### 阶段与顺序

- 三个阶段依次进行：token 与主题 → 基础组件 → 逐页迁移。前一阶段完成并验证后才开始下一阶段。页面迁移内部按区域拆分，各区域之间尽量相互独立。
- 不改协议、不改 daemon、不改数据模型。所有工作都在 app 包内，外加 Electron 窗口初始背景色。

### token 与主题

- 语义色新增或重定义以下角色（命名在实现时对齐现有 token 命名风格）：
  - 画布（canvas）与外框（chrome）
  - 卡片 / 浮层表面（surface）
  - 用户消息气泡表面（message surface）
  - 侧栏底色，以及侧栏行的 hover、active、selected 三态和选中描边
  - 文字三级（主、次、弱）
  - 边框与输入框边框
  - 强调色（亮 #1b4ed8 / 暗 #346bf1）及其前景色
  - diff 新增 / 删除行底色与色条
  - Composer 阴影；暗色下的顶部内高光
- 默认亮色和暗色取值来自 t3code 默认主题色板（详见 research/reference-t3code.md 的色值表）。暗色侧栏比画布更暗（侧栏 #000，画布 #0a0a0a）。
- 状态色保留"每个状态信号一个 token"的现有规则和生成方式，只调整生成输入以适配新色板，不手调单个值。
- 新设计接管现有的默认亮色和暗色主题 id，用户已保存的主题选择无需迁移；其余内置主题 id 不变。
- 旧主题与插件主题缺失的新角色，由一个纯函数从该主题已有的语义色派生。原型里的派生形状如下（来自原型，仅示意决策）：

  ```ts
  function deriveSidebarRows(base: SemanticColors) {
    // 旧主题没有这些角色，从前景色按比例叠加得到
    return {
      sidebarRowHover: withAlpha(base.foreground, 0.04),
      sidebarRowSelected: withAlpha(base.foreground, 0.075),
    };
  }
  ```

- 圆角梯度：6 / 8 / 10 / 14 / 18 / 22，分别对应 sm / md / lg / xl / 2xl / 3xl。控件高度三档：24 / 28 / 32。图标尺寸 token：默认 16，元信息 12 或 14。
- 字体保持现有的系统字体栈默认值（已是系统字体），继续支持用户在外观设置里改字体和字号。
- 毛玻璃（半透明表面加背景模糊与饱和度）和全局噪点只在 Web 和 Electron 上生效，通过平台文件扩展或 web 专属样式实现；原生端使用同一表面色的不透明版本。

### 基础组件

- **Text**：用途命名的字号阶梯，每档自带行高，参考 multica 的命名、t3code 的取值：micro 11、caption 12、label 13、body 14、body-lg 15、title-sm 16、title 18、title-lg 20、display 24。另有一个供长文阅读的正文变体（14，行高更松）。阶梯按用户外观设置里的基础字号换算，不写死像素值。颜色只接受三级文字 token 和语义色。
- **Row**：前置槽 / 内容区（标题加可选的元信息行）/ 后置槽。hover、选中、按下三态取自新的行 token，选中态在 hover 时仍可辨认。hover 遵循项目现有的唯一 hover 模式（外层 View 负责 pointer enter/leave，内层 Pressable 负责按下）。后置的悬停操作按 `isHovered || isNative || isCompact` 显示。
- 现有控件（按钮、下拉菜单、右键菜单、Combobox、Tooltip、开关、分段控件、输入框、sheet、确认对话框）的外观在这一阶段对齐新 token，对外接口不变。

### 逐页迁移

- **左侧栏**：原型的 V1。行结构、数据来源、分组模式、显示偏好都不变。选中态改为细描边加浅底色；需要处理的工作区（现有 attention 状态）标题加粗；状态槽使用统一的状态图标（运行中为低频旋转环）。
- **工作区**：tab 高约 26、圆角 8，当前 tab 有底色，关闭按钮在 hover 或选中时出现，未聚焦 pane 的当前 tab 用更弱的底色。pane 头部只有一条底边线。分屏保留。
- **对话流**：
  - 用户消息：右对齐，最大宽度 80%，圆角 18，使用 message surface。
  - agent 回复：无背景，文字为主前景色的约 86%。
  - 工具调用：每项一行（约 26），可折叠；展开内容缩进，放在浅底等宽框里，有最大高度。
  - 思考过程：折叠为一行。
  - 代码块：带语言标签和复制按钮，暗色下无边框。
  - 改动文件汇总：一块，显示文件数、±统计和打开 diff 按钮。
  - 运行中状态行：低频扫光，用分段动画，不可见时暂停，尊重减少动态。
- **Composer**：圆角 22，低透明度 1px 描边，亮色用 Composer 阴影、暗色用内高光，Web/Electron 带毛玻璃。Agent controls 为 28 高的幽灵按钮；发送和停止为 32 的圆形按钮。上下文信息条附着在 Composer 底部。窄宽度时左侧控件可以截断，发送和停止按钮不参与压缩。
- **Explorer sidebar 与 diff**：tab 样式与工作区 tab 一致。改动文件行 28 高。diff 行底色为浅绿 / 浅红并带 3px 左侧色条，折叠分隔线显示"N unmodified lines"，文件头吸顶。
- **设置页**：分组卡片圆角 14，行最小高 56，左边标题加说明，右边控件。
- **菜单与对话框**：菜单圆角 10，菜单项高 30、圆角 6；对话框圆角 18，带底部按钮区。危险操作的红色按钮只出现在确认对话框里（沿用现有规则）。
- **Electron 窗口**：初始背景色改为新画布色（亮 / 暗）。
- 所有迁移保持 testID 和英文 UI 文案逐字不变。迁移中碰到的文件，顺带把硬编码的颜色和图标尺寸换成 token；没碰到的文件不做全局清扫。
- 设计文档（design.md 及相关 spec）随每个阶段改写对应章节，改的是已经过时的内容，不在末尾追加。

## 测试决策

- **好测试的标准**：只断言外部可见行为，比如某个主题下某个角色的最终颜色、组件渲染出的计算样式、用户可见的状态切换；不断言内部实现细节。测试必须确定性，不做条件断言或弱断言。
- **测试接缝一（主接缝）：主题注册表。** 对每一套注册主题（全部内置主题，外加一个插件主题样例）断言：新角色全部有值、派生结果确定、文字与背景对比度满足现有阈值、侧栏行三态之间对比度可辨。先例：现有的主题单测、终端对比度单测、控件几何单测。
- **测试接缝二：新基础组件的 browser 测试。** 对 Text 的各档、Row 的 hover / 选中 / 按下状态在真实浏览器里断言计算样式，并断言原生降级路径（没有毛玻璃）。先例：状态徽章和 overlay root 的 `*.browser.test`。
- **页面迁移不新增接缝**：现有 Playwright e2e 必须保持通过（依靠 testID 和英文文案不变）；约 24 个断言 CSS、约 56 个断言几何尺寸的 spec，凡是本来就要改变的设计，随迁移更新断言。视觉验收用 Electron 桌面端亮 / 暗截图，按 QA 文档的证据要求，与原型对照。
