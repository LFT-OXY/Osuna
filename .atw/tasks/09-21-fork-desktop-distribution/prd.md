# 桌面端 fork 分发配置改造

**Triage:** ready-for-agent

## Problem Statement

我把 `getpaseo/paseo` fork 成 `LFT-OXY/Osuna` 做了二次开发，现在想把桌面端打包
发给小团队用。但仓库里整套打包和发布流程是为上游准备的，直接拿来用会出三类问题：

1. **装上去会被官方版覆盖。** 打包产物里的更新源指向 `getpaseo/paseo`。团队成员
   装完内部版，客户端自动去查上游 Release，发现版本更高就静默升级——二次开发的
   功能全部消失，而且没人会意识到发生了什么。
2. **根本打不出 macOS 包。** 配置要求 Apple 公证，我没有 Apple Developer 账号。
3. **发布流程跑不通。** 发版脚本会往公共 npm 发布 `@getpaseo/*` 包，我没有那个
   scope 的权限；CI 的收尾步骤又硬性要求 mac/linux/windows 三份更新清单齐全，
   缺一份 Release 就永远停在草稿状态。

我没有 Windows 机器，也不需要 Linux 包。

## Solution

把桌面端的分发链路整体切到本 fork 名下，团队成员装的是「我的版本」，更新也只从
我的仓库来：

- 更新源指向 `LFT-OXY/Osuna`。仓库是 public，客户端不需要任何凭据。
- macOS 出无签名、不公证的包。团队首次打开需要手动放行一次，这是没有证书时的
  既定代价，写进分发说明。
- Windows 交给 CI 的 `windows-latest` runner 构建。
- 去掉 Linux 构建，同时把「发布需要哪些平台」这条规则从 CI 脚本里的 shell 数组
  上移到已有的清单校验脚本，让它进入测试覆盖。
- 提供一条不碰 npm 的发版路径：改版本号、打 tag、推送，由 CI 完成构建和发布。

应用本身的身份（`appId`、`productName`、`paseo://` 协议、`~/.paseo` 数据目录）
一律不动——团队成员不需要和官方 Paseo 共存。

## User Stories

1. 作为团队成员，我想从一个链接下载到桌面端安装包，这样我不用自己配开发环境就能用上。
2. 作为团队成员，我想装上内部版后它保持是内部版，这样我依赖的二次开发功能不会凭空消失。
3. 作为团队成员，我想在应用内收到内部版的更新提示，这样我不用盯着仓库看有没有新版本。
4. 作为团队成员，我想更新后装上的仍然是内部版，这样更新不会把我换回官方版。
5. 作为 macOS 用户，我想在首次打开被系统拦住时有一份明确的放行步骤，这样我不用猜该怎么办。
6. 作为 macOS 用户，我想按自己的芯片拿到对应的包（Apple Silicon 或 Intel），这样应用能正常跑。
7. 作为 Windows 用户，我想拿到一个能双击安装的安装包，这样我不需要命令行。
8. 作为 Windows 用户，我想在 SmartScreen 警告时知道这是预期的，这样我不会以为文件有问题。
9. 作为维护者，我想在没有 Apple Developer 账号的情况下也能出 macOS 包，这样不用为内部分发花年费。
10. 作为维护者，我想在只有 Mac 的情况下也能出 Windows 包，这样我不用准备一台 Windows 机器。
11. 作为维护者，我想用一条命令发版，这样我不用记住一串手工步骤。
12. 作为维护者，我想发版时不触碰公共 npm，这样不会因为没有 `@getpaseo` 权限而中途失败。
13. 作为维护者，我想在发版失败时立刻看出是哪个平台出的问题，这样我不用翻整个 CI 日志。
14. 作为维护者，我想在不发布的前提下先出一次产物自己试装，这样我不会把坏版本推给团队。
15. 作为维护者，我想 Linux 不再占用 CI 时间，这样发版更快。
16. 作为维护者，我想在以后团队出现 Linux 机器时能低成本加回来，这样今天的删减不会变成死路。
17. 作为维护者，我想「发布需要哪些平台」这条规则有测试覆盖，这样改错了能在 CI 里发现，而不是在一次卡住的发布里发现。
18. 作为维护者，我想清楚知道哪些配置是为 fork 改的，这样以后从上游同步代码时知道要保住什么。
19. 作为维护者，我想本地也能出一个 macOS 包快速验证改动，这样我不必每次都等 CI。
20. 作为维护者，我想应用的数据目录和身份保持不变，这样我的开发环境和已有 agent 状态不受影响。

## Implementation Decisions

### 更新源切换

`packages/desktop` 的 electron-builder 配置中，GitHub publish 的 owner/repo 改为本
fork。electron-builder 会把这段烘进安装包内的更新配置文件，客户端据此确定更新源。
仓库为 public，`electron-updater` 无需额外凭据。

更新逻辑本身不改。更新服务只在应用处于打包状态时才发起检查，这个行为保持原样。

### macOS 无签名

关闭 macOS 的公证要求。`hardenedRuntime` 在未签名时不生效，保留与否不影响结果，
按改动最小原则不动它。

CI 的 macOS 作业移除 Apple 证书与公证相关的环境变量注入——这些 secret 在本仓库
不存在，留着会让作业在一个误导性的位置失败。

本地构建时通过关闭签名身份自动发现来出无签名包，这条命令写进文档。

### 去掉 Linux

从桌面发布工作流中移除 Linux 构建作业，以及收尾作业中对 Linux 更新清单的下载和
合并。

### 平台清单上移（测试接缝）

「一次发布需要哪些平台的更新清单齐全」这条规则，目前写在发布工作流的一段 shell
数组里，没有任何测试覆盖。改错的表现是 Release 永远停在草稿状态，而且只有在真实
发布时才会暴露。

把期望平台集合变成清单校验脚本的一个输入参数，工作流只负责传参。该脚本已经是导出
的纯函数并有配套测试文件，复用这个接缝，不新建。

校验脚本需要同时承担两件事：确认传入的清单本身合法（现有行为），以及确认期望平台
对应的清单都到齐了（新增行为）。期望平台集合是必填参数，不是可选项——工作流是唯一
调用方，留一条「不传就不检查」的路径等于把这条规则又变回可以静默失效。

期望集合在工作流里由一个顶层环境变量声明，收尾作业的对账循环和校验调用共用它，
构建结果判定也并进同一个循环，避免平台清单散落在多处。

**校验必须早于上传。** 实现时发现上游次序（先传后验）的前提是「Release 还是草稿，
客户端读不到」，而手动派发可以针对一个已经转正的 Release 重跑，那时未经校验的清单
一上传就会被客户端读到。代价是：首轮发布若有平台失败，这一轮一份清单都不会上传，
后续只能用全平台重跑补齐，而不能用单平台 tag——这条写进发版文档。

反向操作（从集合里去掉一个平台）不会自动清理该平台遗留在既有 Release 上的清单，
按手动 `gh release delete-asset` 处理，同样写进文档。

### 发版路径

现有发版脚本在打 tag 之前会向公共 npm 发布工作区包，fork 没有对应 scope 的权限。
新增一条只做「改版本号 → 打 tag → 推送」的发版路径，跳过 npm 发布环节。tag 推送
后由现有的桌面发布工作流接管。

不新建工作流。现有工作流的 tag 触发规则和手动派发入口都保留，手动派发用于「只出
产物不发布」的试装场景。

新路径严格只做这三步，连 `release:check` 也不跑——它的主体是针对 `@getpaseo/*` 的
七个 `npm pack --dry-run`，与「不碰 npm」直接冲突。构建门禁改为文档要求的前置
format / lint / typecheck。只提供 patch 与 minor 两档，major 沿用仓库既有约束：
不由 agent 自选。

### 版本号

沿用当前 `0.8.x` 版本线，不引入独立版本号方案。更新检查只看本仓库的 Release，与
上游同号不构成技术冲突。代价记在 Further Notes。

### 应用身份

`appId`、`productName`、`executableName`、`paseo://` 协议、`~/.paseo` 数据目录
全部保持不变。这些只在需要与官方 Paseo 共存时才必须改，当前判断为不需要。改动它们
会牵出产品名的六处硬编码以及 server 包的数据目录定义，等同于重做一遍已废弃的
rebrand 分支。

## Testing Decisions

好的测试只验证外部可观察的行为。这个任务的绝大部分改动是声明式配置——更新源地址、
公证开关、CI 作业增删——它们没有合适的单元测试接缝，为其造接缝只会增加维护负担而
不增加信心。这类改动的验证方式是构建产物本身和一次真实的 CI 运行。

**唯一进入测试覆盖的是平台清单规则。** 在清单校验脚本已有的测试文件中扩充用例：

- 期望平台齐全时通过
- 期望 mac 与 windows、但缺少其中一份时报错，且错误信息点名缺哪个
- 期望集合中不含 Linux 时，Linux 清单缺席不应报错
- 现有的清单内容校验行为（发布时间、灰度时长、macOS 系统版本下限）不回归

先照现有用例的写法写：直接调用导出函数断言抛错信息，并通过子进程调用 CLI 断言退出码。

**人工验证**（配置改动只能这样验）：

- 本地出一个 macOS 无签名包，安装后确认应用内的更新源指向本 fork
- 手动派发一次工作流且不发布，确认 mac 与 windows 产物都产出、无 Linux 作业
- 正式发一个版本，确认 Release 脱离草稿状态、团队成员能收到更新提示且更新后仍是内部版

第三条必须在告知团队之前跑通,它是唯一能证伪「更新会跳回官方版」的检查。

## Out of Scope

- 改应用身份：`appId`、`productName`、协议 scheme、数据目录。
- 代码签名：Apple Developer 账号、Windows 代码签名证书。本次明确接受无签名分发。
- Linux 分发。
- 向公共 npm 发布任何工作区包。
- 移动端（iOS / Android）与 Docker 的发布链路。
- 灰度策略调整。沿用现有默认。
- 自动更新的产品行为改动，包括检查频率、渠道语义、灰度准入逻辑。
- 从上游同步代码的流程。

## Further Notes

**版本号与上游同号。** 内部版仍是 `0.8.x`，团队成员从版本号看不出装的是内部版还是
官方版。技术上无冲突，但排查问题时可能造成混淆。若以后成为实际困扰，再单独处理。

**公证关闭后 macOS 没有打包冒烟可跑（已确认）。** electron-builder 在未发生签名时
会跳过 `afterSign` 钩子（`app-builder-lib` 的 `platformPackager` 打一条 warning 后
略过），而 macOS 的冒烟只挂在 `afterSign` 上——`afterPack` 那条只覆盖 Linux 和
Windows。所以它不是「会失败」，而是「不会运行」。按此结论把 macOS 作业里的
`PASEO_DESKTOP_SMOKE` 与冒烟诊断上传一并移除，不留死配置；Windows 作业的冒烟保留。
macOS 包的验证退化为人工装一次点开。

**从上游同步代码时的冲突面。** 本次改动集中在 electron-builder 配置的 publish 段
与 mac 段、桌面发布工作流、清单校验脚本、根目录发版脚本。上游改动这些文件时会冲突,
合并时要保住 fork 这一侧的值。
