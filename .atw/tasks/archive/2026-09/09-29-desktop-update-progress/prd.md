# 桌面端应用更新：手动下载与下载进度

范围只有 Electron 桌面端的应用更新。iOS/Android（走应用商店）、浏览器 Web 版、本地 daemon 更新都不在内。

## Problem Statement

桌面端的应用更新对用户是个黑盒：

- 发现新版本后，更新器在后台静默下载，用户不知道正在下载、下了多少、还要多久。
- 下载期间侧栏什么都不显示，只有设置 → 关于那一行写着「正在下载...」，没有百分比。所以用户多半从没见过更新卡片，直到它突然出现并说「已准备好安装」。
- 下载完全是自动的，用户事先不知情，也没有机会拒绝。
- 点「安装并重启」后，macOS 上还要取回并校验整个安装包，最长约 60 秒，这期间只显示「正在安装...」。
- 侧栏卡片点「安装并重启」直接重启，没有任何确认；设置页却会先弹系统确认框。两个入口行为不一致。
- 侧栏卡片和设置页各自维护一份更新状态，可能互相不同步。
- 卡片点 × 关闭后是永久记住的，这个版本以后都不会再提示。

## Solution

不再静默下载，由用户决定何时下载，整个更新过程都在左侧栏底部现有的更新卡片里完成：

| 阶段 | 标题 | 描述 | 按钮 | × |
|---|---|---|---|---|
| 发现更新 | 有可用更新 | `vX 可用 · 查看更新内容`（链接） | 稍后 / **更新** | 本次运行隐藏 |
| 下载中 | 正在下载更新 | 进度条 + `42% · 41.4 / 98.6 MB · 3.2 MB/s` | 取消（取消请求进行中为禁用的「正在取消…」） | 隐藏，后台继续下载；下完后卡片重新出现 |
| 已下载 | 更新已下载 | vX 已下载。安装会重启 App，停止正在运行的 agents 并关闭 terminal 会话；退出 App 时也会自动安装 | 稍后 / **安装** | 本次运行隐藏 |
| 安装中 | 正在安装更新 | 正在准备重启…（不确定进度） | 安装中（禁用） | 无 |
| 失败 | 更新失败 | 错误信息 | 重试 / **前往 Releases 手动下载**（取消失败时下载仍在继续，只有 **重试**） | 本次运行隐藏 |

- 「稍后」和 × 都只在本次运行期间隐藏卡片，下次启动再提示，不再永久记住。
- 「取消」中止下载，回到「发现更新」。取消命令本身失败时（下载仍在继续），卡片显示错误和「重试」；主进程阶段一变（例如随后下完），这条错误就过期、不再显示。点「取消」时安装包已经下完、正在校验或改名，取消不再生效，卡片如实进入「已下载」。
- 「安装」点了立即安装，不再二次确认；风险提示写在卡片描述里。
- 设置 → 关于的「检查」「更新」按钮和侧栏卡片共用同一份状态。那一行显示当前阶段的文字（例如「正在下载 42%」），原来的系统确认框去掉。在设置页发起下载，或手动检查发现新版本，都会解除本次运行的隐藏状态，所以离开设置页后侧栏卡片会出现。

## User Stories

1. 作为桌面端用户，我希望有新版本时侧栏出现「有可用更新」卡片并显示版本号，这样不用去设置页也能知道有更新。
2. 作为桌面端用户，我希望更新器在我点「更新」之前不下载任何东西，这样更新不会在我不知情时占用带宽和磁盘。
3. 作为用流量计费网络的用户，我希望能推迟下载，等换到合适的网络再下，这样不会被动消耗流量。
4. 作为桌面端用户，我希望能从卡片直接打开更新内容，这样可以先了解新版本改了什么，再决定要不要更新。
5. 作为桌面端用户，我希望点「更新」后卡片立即进入下载中并显示进度条，这样能确认下载已经开始。
6. 作为桌面端用户，我希望看到百分比、已下载/总大小和当前速度，这样能判断大概还要多久。
7. 作为桌面端用户，我希望在收到第一份进度之前卡片也显示「正在下载」，这样开头那几秒不会显得卡住。
8. 作为桌面端用户，我希望能取消正在进行的下载并回到「发现更新」，这样发现网络不合适时可以停下来。
9. 作为桌面端用户，我希望下载中点 × 只是把卡片收起、下载继续进行，这样卡片不会一直占着侧栏。
10. 作为收起了下载卡片的用户，我希望下载完成后卡片自动重新出现，这样不会错过安装时机。
11. 作为桌面端用户，我希望下载完成时卡片写明安装会重启 App、停止 agents、关闭 terminal 会话，这样我能在不打断工作的时机再装。
12. 作为桌面端用户，我希望点「安装」后立即开始安装，这样不必再点一层确认。
13. 作为桌面端用户，我希望安装交接期间卡片显示「正在准备重启」且不能关闭，这样不会误以为安装卡死或被取消。
14. 作为下载完但选择「稍后」的用户，我希望退出 App 时自动装上这个更新，并且卡片事先告诉过我这一点，这样不用专门找时间重启。
15. 作为 Linux AppImage 用户，我希望卡片不承诺「退出时自动安装」，因为这个平台不会这么做。
16. 作为桌面端用户，我希望下载或安装失败时卡片显示错误原因，并给出「重试」和「前往 Releases 手动下载」，这样自动更新坏了我也有路可走。
17. 作为桌面端用户，我希望点「稍后」或 × 后，本次运行期间不再被同一张卡片打扰，这样可以专心工作。
18. 作为之前点过「稍后」的用户，我希望下次启动 App 时再看到更新提示，这样不会一直停在旧版本。
19. 作为桌面端用户，我希望在设置 → 关于里看到和侧栏一致的更新阶段，包括下载百分比，这样两处的信息不会互相矛盾。
20. 作为桌面端用户，我希望在设置里点「更新」开始下载，离开设置页后能在侧栏卡片继续看进度，这样两个入口是同一件事。
21. 作为在设置里手动检查更新的用户，我希望即使之前点过「稍后」，检查到新版本后侧栏卡片也重新出现，这样手动检查的结果是可见的。
22. 作为在设置里操作的用户，我希望已下载阶段直接在设置页点「安装并重启」就能安装，不再弹系统确认框，这样两个入口的安装方式一致。
23. 作为 Beta 通道用户，我希望下载中切换发布通道会取消当前下载并回到「发现更新」，这样不会装上另一个通道的版本。
24. 作为下载途中退出 App 的用户，我希望下次启动能从「发现更新」重新开始，不会停在一个假的下载中状态。
25. 作为之前已下完但没装的用户，我希望下次点「更新」能立刻进入「已下载」，不必重新下载整个安装包。
26. 作为开了多个窗口的用户，我希望每个窗口的更新卡片都显示同样的阶段和进度，这样不会因为窗口不同而看到不一样的信息。
27. 作为 Intel Mac 上用 Rosetta 运行的用户，我希望 Rosetta 提示仍然优先显示，更新卡片排在它后面，这样更重要的提示不会被挡住。
28. 作为使用任一支持语言的用户，我希望所有新文案都有本地化，这样界面不会混进英文。
29. 作为没有新版本的用户，我希望侧栏不出现任何更新卡片，设置页照常显示「已是最新版本」。

## Implementation Decisions

### 状态归属

- 主进程持有下载阶段和最新一份进度，是唯一的事实来源。渲染进程只做镜像，所以多个窗口、侧栏和设置页看到的状态一致。
- 每个窗口的渲染进程只保留**一个**应用更新状态机实例，侧栏卡片和设置页共用它。现在每个用到更新 hook 的组件各建一份，需要改成单例。

### 桌面主进程：更新服务

- 关闭 electron-updater 的自动下载，在那行代码旁用一句注释说明：不在用户不知情时下载。
- 自动检查（启动时一次、之后每 30 分钟）和灰度发布准入规则都不变，只是检查只负责发现新版本，不再触发下载。
- 更新服务对外的动作拆成四个：
  - **检查**：发现与准入规则不变。下载或安装进行中不访问更新源，直接返回当前快照，避免清单变化替换掉正在处理的目标版本。发布通道一律取自主进程保存的桌面设置，渲染进程不传通道：渲染进程的设置是乐观更新、窗口之间不同步，别的窗口可能还拿着旧通道。
  - **下载**：对已准入的目标版本开始下载，重复调用是幂等的。
  - **取消下载**：通过 electron-updater 的取消令牌中止下载。取消不算错误，阶段立即回到「发现更新」。取消、下载、切换通道和检查共用一条队列：取消一定排在已发出的下载请求之后，新的下载要等被取消的那次落定才开始（否则 electron-updater 会把进行中的旧 promise 还回来）。
  - **安装**：只在目标版本已下载时执行，包括停 daemon、`quitAndInstall`、等待安装交接、失败后把 daemon 拉起来。原来那个先下载再安装的合并动作取消，未下载时调用安装返回「未安装」，而不是偷偷开始下载。安装前不再重新检查更新源，直接安装已下载的目标版本。
- 服务订阅 electron-updater 的 `download-progress` 事件，记录最新的 `{ percent, transferred, total, bytesPerSecond }`（`percent` 是 0–100），写进快照的 `progress` 字段。`progress` 只在下载中阶段有值：每次开始下载先清空，第一份进度到达前为 `null`；不在下载中时到达的进度事件直接丢弃。
- 服务对外提供一份**更新状态快照**：阶段（无更新 / 发现更新 / 下载中 / 已下载 / 安装中 / 失败）、目标版本、最新进度、错误信息，以及当前平台是否会在退出时安装。检查结果里带上这份快照，渲染进程挂载时直接调用检查就能拿到当前状态，不需要额外的查询命令。快照带单调递增的 `revision`，命令返回值和推送事件乱序到达时，渲染进程丢弃较旧的一份。失败项记录是哪个动作失败（下载 / 安装）；手动检查会清掉同一版本的失败，自动检查保留，错误不会被后台检查悄悄抹掉。
- 快照每次变化都通过现有的 `paseo:event:*` 通道广播给所有窗口。进度事件的频率跟随 electron-updater 自身的节流（大约每秒一次），不另外加一层节流。
- 切换发布通道由保存设置触发（`patch_desktop_settings` 写入后回调更新服务的 `switchReleaseChannel`），不由「检查带来的通道和上次不同」判断，否则拿着旧通道的窗口会误取消别的窗口发起的下载。通道确实变了时：正在下载就先取消，再清空更新状态，然后主进程自己按新通道做一次自动检查并广播，渲染进程按新通道发起的检查即使先到也不影响结果。安装交接期间切换通道会被忽略（App 马上要重启；万一安装失败，要等后续自动检查纠正）。
- 退出时安装（`installUpdateOnQuit`）：只有已下载的版本才会在退出时安装，Linux AppImage 仍然跳过（由快照里的 `installsOnQuit` 统一判断）。退出前仍做一次自动检查：检查失败，或清单出现了比已下载版本更新的版本时，这次退出不安装，也不在退出途中补下载（旧实现会补下载，这与「从没点过更新就不安装任何东西」冲突）。自动检查发现更新的版本时，已下载的旧版本本来就会退回「发现更新」。
- 下载途中退出 App 不续传。下次启动时如果 electron-updater 缓存里已经有完整的安装包，点「更新」会立即走到「已下载」。
- 渲染进程和主进程随同一个桌面安装包一起发布，这些 IPC 命令和事件可以直接改，不需要 `COMPAT` 兼容层，也不涉及 daemon 的 WebSocket 协议。

### 渲染进程：应用更新状态机

- 状态重新划分为：`idle`、`checking`、`up-to-date`、`available`（发现更新）、`downloading`、`downloaded`、`installing`，失败按失败的动作分为 `check-failed`、`download-failed`、`cancel-failed`、`install-failed`。「重试」重做失败的那个动作；除取消失败（下载仍在继续）只给「重试」外，都保留「前往 Releases 手动下载」入口。卡片只显示一个失败，后发生的优先：失败阶段里手动检查再失败，显示检查错误、「重试」走检查。静默检查不清掉本地错误。现有的 `pending`（语义是「后台自动下载中」）和靠轮询等待下载就绪的逻辑都删掉，改为订阅主进程推送的快照。
- 动作：`check`、`download`、`cancelDownload`、`install`，以及本次运行的隐藏和解除隐藏。
- **本次运行的隐藏**保存在内存里，不持久化，按窗口生效：
  - 用户点「稍后」或 × 时设置隐藏。
  - 在设置页手动检查发现新版本、在设置页发起下载时解除隐藏。「发现」指手动（非静默）检查返回 `hasUpdate` 且阶段不是下载中：下载中的检查不访问更新源、只返回当前快照，下载中被 × 收起的卡片仍等下完再出现。发起下载不分入口一律解除（卡片上发起时本来就可见）。
  - 进入「已下载」时自动解除隐藏，不论之前在哪个阶段被隐藏：「已下载」是一张新卡片，而下载只可能由用户在某个窗口里主动发起（例如窗口 A 点了「稍后」、窗口 B 点了「更新」，下完后 A 也会出现）。
  - 进入失败时也解除隐藏，让错误能被看到：下载、安装失败，以及用户手动检查、取消等命令失败。已在失败中、被自动检查保留下来的失败不解除。
  - 安装中阶段不可关闭，也不受隐藏影响：之前点过「稍后」、再从设置页安装时，卡片照样显示安装中。
- 静默自动检查失败时继续保持现状，不打扰用户。
- 单例由 `DesktopAppUpdaterProvider`（`desktop/updates/desktop-app-updater-provider.tsx`）持有，挂在 `app/_layout.tsx` 的 `RuntimeProviders` 下。它还统一提供 `isDesktopApp`，`useDesktopAppUpdater` 只从 context 读取。
- 自动检查只在 provider 里启动一份：`startAutomaticUpdateChecks({ updater, timer })` 负责启动时的静默检查和每 30 分钟一次的检查（原来 `pending` 期间每 10 秒一次的复查随 `pending` 一并删掉）。通道由主进程决定，所以 provider 不读桌面设置，也不随通道变化重启调度。
- 进入设置页不再触发静默检查。设置页读的是共享状态，要刷新就点「检查」。

### 侧栏更新卡片

- 继续通过现有的侧栏提示 API 注册卡片。不传持久化的关闭键，改用 `onDismiss` 回调去设置本次运行的隐藏；安装中传 `dismissible: false`。优先级保持 200，排在 Rosetta 提示（300）后面。
- 卡片描述器（由状态推导标题、描述、按钮）继续做成纯函数，按上面 Solution 那张表输出五个阶段。
- 下载中的进度条放在卡片描述里，现有描述本来就接受任意 ReactNode。仓库里没有通用的进度条组件：文件下载提示里那条是它自己私有的，这次不去抽公共组件，在更新卡片里写一个最小的实现，样式参照它。
- 大小和速度按 MB 和 MB/s 格式化，保留一位小数；不显示剩余时间。MB 按 1024² 字节换算，与文件下载提示的 `formatSpeed`（`stores/download-store.ts`）一致。百分比向下取整，下载完成前不会显示 100%。
- 整行进度文字走 i18n key `desktop.updates.callout.downloadProgress`（`{{percent}}% · {{transferred}} / {{total}} MB · {{speed}} MB/s`），单位随语言：法语 `Mo`，俄语 `МБ`，其余语言用 `MB`。
- 进度条高 4px，轨道 `surface3`，填充 `primary`，全圆角；DownloadToast 那条 3px、`surface2` 轨道放在侧栏上太淡。填充宽度每秒都在变，走 `inlineUnistylesStyle`，不进 Unistyles 的 CSS 注册表（`docs/unistyles.md`）。
- 「查看更新内容」链接复用现有的 changelog 打开逻辑。

### 设置 → 关于

- 那一行的状态文字按新阶段显示，下载中显示百分比（`desktop.updates.status.downloadingWithPercent`，和卡片一样向下取整，共用 `toWholeDownloadPercent`），已下载时附上重启风险提示（复用卡片的 `desktop.updates.callout.restartWarning`，两处同一句话）。
- 主按钮随阶段变化：发现更新时是「更新」（开始下载，不带版本号）；下载中禁用；已下载时是「安装并重启」，点了直接安装；安装中禁用。「检查」按钮保持不变。
- 去掉安装前的系统确认框。
- 失败时继续显示「前往 Releases 手动下载」（与卡片共用 `offersManualDownload`，取消失败不显示）。设置页没有「重试」，失败阶段主按钮禁用；点「检查」清掉同一版本的失败后可以重新下载。

### 文案

- 新增和修改的文案全部走 i18n，补齐全部 9 种语言。不再使用的 key（例如 `pending*` 系列、「安装并重启」的旧确认框文案）一并删除。

## Testing Decisions

好的测试只从模块的对外行为断言：给定输入或事件序列，看输出的状态快照、描述器，以及发出去的命令。不断言内部变量，也不断言调用顺序这类实现细节。

测试切面有两个，分别对应 IPC 边界两侧。这条边界本身就是进程边界，没法合并成一个：

1. **桌面更新服务**：用假的更新器运行时驱动。沿用 `app-update-service.test.ts` 已有的假运行时写法，再补上下载进度、取消和下载失败这几个事件。要覆盖：
   - 检查不会触发下载；
   - 下载时快照随进度事件更新并广播；
   - 取消后回到「发现更新」且不报错；
   - 未下载时调用安装返回未安装，并且不会开始下载；
   - 已下载时安装走完安装交接，失败时带上失败原因；
   - 下载中切换通道会取消下载、清空状态并按新通道重查；拿着旧通道的窗口检查不会取消下载；
   - 退出时安装只对已下载的版本生效。
2. **渲染进程更新状态机和卡片描述器**：用假端口驱动。沿用 `desktop-app-updater.test.ts` 和 `test-utils/fake-desktop-app-updater-port.ts`，给假端口补上下载、取消命令和推送快照的能力；描述器沿用 `resolve-update-callout.test.ts` 的纯函数测法。要覆盖：
   - 各阶段对应的标题、按钮和是否可关闭；
   - 本次运行隐藏的设置和解除规则（手动检查、从设置页下载、进入已下载、进入失败）；
   - 推送的快照正确驱动状态迁移；
   - 静默检查失败时不打扰用户。

- 不为卡片组件本身写渲染测试。卡片的逻辑都在描述器里，组件只负责把描述器的输出渲染出来。
- 真实的下载进度、Squirrel 安装交接和重启只能在打包后的 App 里验证，交给发版前的人工 QA（见 `docs/qa.md`）。dev 桌面端里只能用注入的假状态检查五个阶段的外观。

## Acceptance Criteria

- [x] 打包版发现新版本后，在用户点「更新」之前不会下载任何更新文件；侧栏出现「有可用更新」卡片，显示版本号和「查看更新内容」链接，按钮是「稍后 / 更新」。
- [x] 点「更新」后卡片进入下载中，进度条随下载推进，显示百分比、已下载/总大小和速度；收到第一份进度之前显示「正在下载」。
- [x] 下载中点「取消」会中止下载，卡片回到「发现更新」，不出现错误提示。
- [x] 下载中点 × 会收起卡片，下载继续；下载完成后卡片自动以「已下载」阶段重新出现。
- [x] 「已下载」阶段写明安装会重启 App、停止 agents、关闭 terminal 会话，并说明退出时也会自动安装（Linux AppImage 不显示这句）；点「安装」直接开始安装，没有二次确认。
- [x] 安装交接期间卡片显示不确定进度且不能关闭；交接失败时卡片进入失败阶段，给出「重试」和「前往 Releases 手动下载」。
- [x] 下载失败时卡片进入失败阶段，显示错误信息，给出同样两个按钮。
- [x] 「稍后」和 × 在本次运行期间隐藏卡片；重启 App 后再次提示；不写入持久化的关闭记录。
- [x] 设置 → 关于与侧栏卡片显示同一阶段，下载中显示百分比；在设置里点「更新」开始下载，离开设置页后侧栏卡片显示同一份进度；已下载时点「安装并重启」直接安装，不弹系统确认框。
- [x] 在设置里手动检查发现新版本后，之前点过「稍后」的卡片重新出现。
- [x] 下载中切换发布通道会取消下载，回到「发现更新」（或在新通道没有更新时显示已是最新）。
- [x] 下完没装就退出 App 时，会在退出时安装该版本（AppImage 除外）；从没点过「更新」的用户退出时不会安装任何东西。
- [x] 多个窗口同时打开时，各窗口卡片的阶段和进度一致。
- [x] 新文案补齐 9 种语言，旧的无用 key 已删除。
- [x] 两个测试切面的测试通过，`npm run typecheck` 和 `npm run lint` 通过。

## Out of Scope

- iOS/Android 的应用更新（走应用商店），浏览器 Web 版。
- 本地 daemon 的更新流程（`run_local_daemon_update`）。
- 在应用内渲染 release notes 正文。只保留「查看更新内容」链接。
- 下载断点续传、暂停后继续。
- 剩余时间估算。
- 抽取通用进度条组件，或改造文件下载提示 `DownloadToast`。
- 修改灰度发布规则、发布渠道配置，或 macOS 签名和安装交接的超时时长。
- 「跳过这个版本」一类的永久忽略功能。

## Further Notes

- 这份 spec 的决定来自 2026-09-29 的问答。中途试过两种方案：模态弹窗，和右下角独立浮窗。用户在 dev 桌面端看过现有侧栏卡片后，决定直接复用它。
- 现有持久化存储里可能残留旧格式的关闭记录（`desktop-update:<status>:<version>`）。新卡片不再使用持久化的关闭键，这些残留不会再被读到，不需要迁移。
- electron-updater 做差量下载（blockmap）时，`total` 可能小于完整安装包的大小。进度条按事件里给的 `total` 显示即可。
