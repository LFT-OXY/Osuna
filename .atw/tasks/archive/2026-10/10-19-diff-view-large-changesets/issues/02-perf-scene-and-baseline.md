# 02 — 固定性能场景与改前基线

**What to build:** 搭出 prd Testing Decisions 里的固定场景，量出现在的数字，作为后面每张工单的对照。不改任何产品行为。

场景：200 个已有文件，每个约 2000 行、各改约 50 行；50 个新建文件；一个改动约 3 万行的 lock 文件；若干 `.sql`、`.sh`、`.toml` 文件；一个模拟 Agent 的脚本，每 0.5 秒改一个文件，持续 1 分钟。场景生成要确定（同样的输入得到同样的仓库），能重复跑。

要量的数字：
- daemon 每次刷新的耗时；
- 打开 Changes 面板到看到内容的耗时；
- 模拟 Agent 那 1 分钟里渲染进程的长任务（次数、最长一次）；
- 窗口冻住时的时间具体花在哪：整包解析与校验、`shareCheckoutDiff` 深比较、行模型重建、绘制，按这几段拆开；
- `.sql`/`.sh`/`.toml` 的高亮在 daemon 刷新耗时里占多少。

扩展现有的 `git-diff-bottleneck.local.e2e.test.ts`（daemon 侧）和 `diff-performance.spec.ts` 及其 baseline 文件（浏览器侧），保持环境变量门控，不新建 npm 脚本。桌面版数字在 dev Electron 里按 Playwright CDP 做法量，用 PerformanceObserver 记录 longtask。

**停下的条件**：如果基线显示冻住主要来自整包解析、深比较这类第二期才能解决的部分，或者某条合格标准（打开 ≤2s、无 >0.5s 冻住、刷新耗时 ≤1/5）明显不现实，就停下，把数据和建议带给用户，不自行放宽标准，也不继续后面的工单。
