# 合并上游 Paseo v0.9.0

**Status:** ready-for-agent

依据：`research/discovery.md`（2026-10-10 的模拟合并数据、冲突清单、访谈逐条确认的决定）。相关既有决定：ADR 0001（macOS 自签名证书）、ADR 0002（改名止于桌面 App 身份）、`docs/release.md` 的「Fork 分发」一节、`docs/protocol-compatibility.md`。

## Problem Statement

Osuna 在 2026-09-16 从上游 `getpaseo/paseo` 的 main 分出，基点是 `0f20e6dfe`，位于上游 v0.8.0 与 v0.9.0-beta.1 之间。此后 main 上的 375 个提交全部是 Osuna 自己的，一次也没有合过上游。

上游在这期间发了 v0.9.0（2026-09-22），带来聊天内查找、附件上传显示、PR 标签页自动打开、插件能力扩展、三项性能改进和 Pi 的按模型 thinking 配置。Osuna 用户拿不到这些。按 ADR 0002，手机端用的是官方 Paseo App，它会随上游继续升级，Osuna daemon 落后越久，两边靠协议兼容契约维持的距离越大。

拖得越久合并越难：两边已经有 108 个文件都改过，其中 46 个冲突；上游现在到了 v0.11.2。维护者没有做过上游合并，不知道自己的功能会不会被冲掉，也没有一套可以重复的做法。

## Solution

把上游从基点到 v0.9.0 的 29 个提交整版合并进 main，用保留上游历史的 git merge，使下一次合并从 v0.9.0 接着做，而不是从头再来。

合并在单独分支上分三段进行，分段点是上游自己的发布点：v0.9.0-beta.1、v0.9.0-beta.2、v0.9.0。每段结束时分支都能通过检查，全部做完后经一个 PR 并入，main 只变一次。

合并后的 Osuna：

- 多了上游 v0.9.0 的全部功能与修复。
- Osuna 自己的功能一个不少，行为不变。
- Osuna 有意做的产品决定原样保留：桌面身份叫 Osuna、更新与外链只指向本仓库、设置页外观、界面中文、自己的版本号与更新日志。
- 仓库里留下一份合并上游的做法说明，v0.10 之后照做。

## Implementation Decisions

### 合并方式

- 新增一个名为 `upstream` 的 remote 指向上游仓库，并配置为不抓取 tag。Osuna 的 `v0.8.1`–`v0.14.2` 与上游同名不同物，抓上游 tag 会相撞；分段点一律用提交 SHA 引用。
- 从 main 开一条合并分支，在上面依次做三次 merge，每次一个 merge commit：

| 段 | 上游发布点 | 提交 | 累计上游提交数 |
| --- | --- | --- | --- |
| 1 | v0.9.0-beta.1 | `7c1958f5b` | 15 |
| 2 | v0.9.0-beta.2 | `e9d32a17d` | 21 |
| 3 | v0.9.0 | `7f7e60bcb` | 29 |

- 每段的 merge commit 本身就要能通过 typecheck、lint 和该段冲突文件对应的测试。冲突之外的适配（文案、外观、兼容标签）可以紧跟在 merge commit 之后单独提交，但必须在进入下一段之前完成。
- 合并分支经一个 PR 并入 main，方式必须是 merge commit。squash 和 rebase 都会丢掉上游的祖先关系，下一次合并就会重新遇到这 46 个冲突。
- 合并期间 main 有新提交时，把 main 合进合并分支，不对合并分支做 rebase。

### 冲突裁决规则

按顺序适用，前一条优先：

1. **Osuna 有意做的产品决定原样保留。** 桌面 App 身份与数据目录（ADR 0002）、macOS 签名与签名断言（ADR 0001）、更新源指向本仓库、应用与 CLI 的外链只指向本仓库且不含上游文档站 / Sponsor / Discord 入口、设置页外观、设置界面文案走翻译键。
2. **两边重复实现同一功能时，以上游写法为底**，把 Osuna 多出的行为补回去，并用测试证明行为未丢。
3. **其余冲突两边都保留。** 上游的改动落地，Osuna 的功能不丢。

裁决不了的情况（两条规则互相矛盾，或保留两边会改变用户可见行为）停下来问维护者，不自行取舍。

### Pi 的按模型 thinking 配置

目前唯一已知的重复实现。采用上游的形态：模型定义直接携带思考档位列表与默认档位，连同上游在 agent 管理、输入框 agent 控件和 e2e 上的配套改动。Osuna 这边要保住的行为：

- 非推理模型不给思考档位。
- 模型的档位映射里标为不可用的档位不出现。
- 最高的两档只在模型显式映射了才出现。
- 切换模型后，当前档位若新模型不支持，先往更高档找、再往更低档找最近的可用档位。
- 设置档位后回读 Pi 实际生效的档位并以它为准；回读失败时退回请求的档位并记日志，不让设置操作失败。

上游实现已经覆盖的行为不重复实现；没覆盖的在上游形态上补。Osuna 原有针对这些行为的测试用例保留，改为针对合并后的实现。

### 版本号与发版元数据

- 所有工作区的版本号保持 Osuna 当前的 `0.14.2`。上游对依赖项的增删改照收。
- `package-lock.json` 不手工合并，解决完各 `package.json` 后重新生成。
- `CHANGELOG.md` 只保留 Osuna 自己的条目，不搬上游的 0.9.0 系列条目。
- 安卓商店说明里与上游同名的四个文件保留 Osuna 的版本。
- `README.md` 保留 Osuna 的版本。
- Nix 依赖哈希不追：对应的两项检查在 Osuna 上本来就是已知红灯。

### 外链与 `ExternalLink` 组件

- Osuna 已删除通用的外链组件，上游在这个范围内改过它。上游代码需要它才能工作时恢复该组件；恢复只服务于上游的新能力（例如插件请求打开外部链接），不借机恢复已删除的上游入口。
- 插件打开外部链接、从 npm 安装插件是插件能力，保留。
- 上游新代码里指向上游站点的固定链接（文档、迁移指南等），按 Osuna 已有先例处理：有对应内容就指向本仓库，没有就连同承载它的按钮一起去掉。
- 合并前后各统计一次应用与 CLI 源码中的上游站点链接，并入时不得增加。

### 协议

- 两边新增的消息与字段都保留，新字段一律可选，不收窄、不删除、不改必填。
- `server_info.features` 中两边新增的能力开关都在。
- 上游新增的 `COMPAT(...)` 标签，版本号改写为合并后的首个 Osuna 版本（预计 v0.15.0，发版时若不同再统一改）。Osuna 已有的标签不动。
- 合并后 daemon 仍能解析官方 Paseo 手机 App 与旧版 Osuna 客户端发来的消息，反之亦然。

### 界面文案

- 上游新增的翻译键在九种语言里齐全；zh-CN 是真实翻译，不是英文占位。
- 上游在设置界面新增的硬编码英文改走翻译键，并加入现有的源码扫描清单。
- 用词遵循 `docs/glossary.md`。

### 发版流程与 CI

- 桌面发版工作流保留 Osuna 的身份、签名步骤和上传前的签名断言。吸收上游的两项改进：按架构抬高构建的 Node 堆上限、发布产物上传重试。Osuna 已有自己的堆上限设置，合并后只留一处。
- 更新源配置指向 `LFT-OXY/Osuna` 不变。上游在这个范围内没有改它，合并后仍要核对。
- 在 fork 下只保留手动触发的部署工作流，触发条件不变。
- 上游在 CI 中新增的官网样机检查与发布产物上传脚本的测试照收。

### 文档

- 上游对 `docs/` 与 `public-docs/` 的改动照收；与 Osuna 既有决定矛盾的段落按冲突裁决规则 1 处理。
- 在 `docs/release.md` 的「Fork 分发」一节加入从上游同步的做法：不抓上游 tag 及原因、分段点的选取、必须用 merge commit 并入、版本号与更新日志的归属、合并后必须核对的 Osuna 不变量、当前已同步到的上游版本。写约束和坑，不写操作流水账。

## UI and Design

这次不引入新的视觉方向。上游带来的界面照上游的样子落地，只在两处向 Osuna 靠拢：

- **设置页**：上游新增的插件安装与来源变更查看界面，采用 Osuna 设置页现有的卡片、行高与下拉触发器样式（`docs/design.md` 与 `.atw/spec/app/frontend/` 的设计规则适用）。
- **文案**：见上文「界面文案」。

目标视口：Electron 桌面端 1280 宽。原生端免验收。

截图可核对的验收点：

- 设置页任一分区不出现与其他分区不同的卡片圆角或行高。
- 插件页在中文界面下没有英文句子（专有名词、命令、包名除外）。
- 侧栏帮助菜单、欢迎页、更新分区不出现上游文档站、Sponsor、Discord 入口。
- 聊天查找条显示匹配总数，匹配项高亮可见。
- 输入框旁的套餐用量栏在聊天与草稿标签页中都在。
- 终端内容四边留有对称内边距。

## Testing Decisions

好的测试只断言外部行为：给定输入与状态，用户或调用方看到什么。不断言内部函数的调用次数或中间结构。这次是合并而不是新功能，测试的作用是证明两边的行为都还在，因此优先用已有的测试，不新开测试接缝。

### 接缝

1. **CI 全套作业**（最高接缝）。format、lint、typecheck、server-tests（ubuntu / windows）、desktop-tests（ubuntu / windows）、app-tests、sdk-tests、playwright 四个分片、relay-tests、cli-tests 三个分片。上游为自己的功能带来的测试随合并进入这些作业；Osuna 的测试守住 Osuna 的功能。
2. **Pi provider 测试**。沿用现有的以假 Pi 进程驱动的 Pi agent 测试，上文列出的五条 Osuna 行为各有用例。
3. **Osuna 不变量的现有测试**。桌面更新源的单元测试与 e2e、插件脚手架测试、翻译资源测试（各语言键同步、zh-CN 允许清单、已迁移英文不回到源码）。
4. **dev 桌面端实测**。见验收清单。

### 规则

- Osuna 原有的测试不删除、不跳过、不放宽断言。因上游形态变化必须改写的（Pi 那组），改写后覆盖的行为不少于改写前，并在 PR 中逐条对应。
- 上游带来的测试要通过。上游测试断言的内容与 Osuna 有意做的决定矛盾时改测试，并在 PR 中说明是哪条决定。
- 本机只跑改动涉及的单个测试文件，整套测试交给 CI。合并分支尽早开成草稿 PR，每段推送后看 CI。
- 本机旧的 Vite 预构建缓存和 `.expo` 类型会掩盖 CI 上会挂的问题，段末复核前先排除这两项。
