# 合并上游 Paseo v0.9.1 与 v0.9.2

**Status:** ready-for-agent

依据：`research/discovery.md`（2026-10-10 的模拟合并数据、冲突清单、访谈逐条确认的决定）。做法沿用 `docs/release.md` 的「Fork 分发 → 从上游同步」，本文只写这一次特有的范围、裁决与验收，不重述那一节。相关既有决定：ADR 0001（macOS 自签名证书）、ADR 0002（改名止于桌面 App 身份）。

## Problem Statement

Osuna 在 2026-10-10 把上游 `getpaseo/paseo` 合到了 v0.9.0，此后与上游的同步点是 `7f7e60bcb`。上游在 v0.9.0 发布后的两天里又发了 v0.9.1 和 v0.9.2，共 62 个提交，几乎全是缺陷修复：daemon 在重启后、残留空 pid 文件、schedules 目录里有杂文件、`config.json` 带 BOM 时起不来；daemon 在观察不了的仓库上占满一个 CPU 核、会话关闭后堆持续增长；Claude 对话回退落到子智能体消息上、越不过没有回复的轮次；多步快捷键在重渲染之间断掉；多选问题卡片里勾选项与「其他」答案不一起提交。Osuna 用户现在还带着这些缺陷。

上游已经到了 v0.11.2。每多拖一个版本，两边同时改过的文件就多一批。这一段是 v0.9.0 之后最小的一步：代码冲突 6 个文件，协议、翻译、外部依赖、桌面打包与签名配置上游都没碰。先把它合掉，后面的 v0.10 才有一个干净的起点。

这一段里有两处两边各做了一遍：Opus 5.5 模型（Osuna 9 月 26 日自己加的，上游在 v0.9.1 加的）和问题卡片（Osuna 9 月 28 日重做了外观与单选交互，上游在 v0.9.2 修了多选）。不处理好，要么 Osuna 的卡片外观被冲掉，要么上游的修复落不进来。

## Solution

把上游从 v0.9.0 到 v0.9.2 的 62 个提交整版合并进 main，用保留上游历史的 git merge，使下一次合并从 v0.9.2 接着做。

合并在单独分支 `merge-upstream-v0.9.2` 上分两段进行，分段点是上游自己的发布点。每段结束时分支都能通过检查，全部做完后经一个 PR 以 merge commit 并入，main 只变一次。

合并后的 Osuna：

- 多了上游 v0.9.1 与 v0.9.2 的全部修复，以及 Opus 5.5 的上游形态、Claude settings.json 里映射的 Fable 模型、Claude 会话的结构化启动参数等小功能。
- Osuna 自己的功能一个不少。行为上只有一处有意的变化：Opus 5.5 的默认思考档位从「高」变为「中」，与上游一致。
- 问题卡片保持 Osuna 的外观与「单选点击即作答」，多选题的勾选项与「其他」答案一起提交。
- 桌面身份、更新源、签名、外链、设置页外观、界面中文、版本号与更新日志继续是 Osuna 的。
- `docs/release.md` 里记录的同步点更新到 v0.9.2。

## User Stories

1. As a Osuna 用户, I want 电脑重启后 daemon 照常启动，即使旧的 PID 被别的进程占了, so that 不用手动清理才能用。
2. As a Osuna 用户, I want 残留一个空的 pid 文件时 daemon 照常启动, so that 一次异常退出不会让它再也起不来。
3. As a Osuna 用户, I want schedules 目录里混进一个不是定时任务的文件时 daemon 照常启动, so that 一个杂文件不会拖垮整个服务。
4. As a Osuna 用户, I want 用带 BOM 的编辑器保存过的 `config.json` 也能被读取, so that 在 Windows 上改配置不会让 daemon 报错。
5. As a Osuna 用户, I want CLI 解析不了 `config.json` 时指出是这个文件, so that 知道该去修哪里。
6. As a Osuna 用户, I want 后台启动在写日志之前就失败时能看到原因, so that 不用猜为什么没起来。
7. As a Osuna 用户, I want daemon 在观察不了的仓库上不占满一个 CPU 核, so that 电脑不发烫、风扇不狂转。
8. As a Osuna 用户, I want 会话关闭后 daemon 的内存不再持续增长, so that 长时间开着不越来越慢。
9. As a Osuna 用户, I want 在「添加项目」里搜索目录时不超时, so that 目录多的机器上也能加项目。
10. As a Osuna 用户, I want 多选问题卡片里勾了选项又填了「其他」时两者一起提交, so that 智能体收到我完整的回答。

## Implementation Decisions

### 合并方式

- 合并分支 `merge-upstream-v0.9.2` 从 main 开出，在上面依次做两次 merge，每次一个 merge commit。上游发布点用提交 SHA 引用，不抓上游 tag。

| 段  | 上游发布点 | 提交        | 本段上游提交数 | 模拟合并的冲突文件（机械性 + 代码） |
| --- | ---------- | ----------- | -------------- | ----------------------------------- |
| 1   | v0.9.1     | `818658520` | 7              | 15 + 2                              |
| 2   | v0.9.2     | `c67b7158b` | 55             | 累计 19 + 6                         |

- 每段的 merge commit 本身通过 typecheck、lint 和该段冲突文件对应的测试。冲突之外的适配紧跟在 merge commit 之后单独提交，进入下一段之前做完。
- 第一段合完就开草稿 PR，目标分支 main，之后每段推送后看 CI。
- 并入 main 用 merge commit，不 squash、不 rebase。合并期间 main 有新提交时把 main 合进合并分支。

### 冲突裁决

沿用 `docs/release.md`「冲突裁决」的三条规则与「停下来问维护者」的条件。本次已由维护者逐条确认的两处：

**Opus 5.5 模型（第一段）。** 以上游的写法为底：

- 清单条目取上游的，包括按模型指定的默认思考档位这一新字段，Opus 5.5 的默认思考档位为「中」。
- 带前缀模型 ID 的归一化取上游的写法，Osuna 为同一问题写的那份去掉。
- Osuna 多出、上游没有的行为保留并继续由测试守着：`us.anthropic.claude-opus-5-5` 及其 1M 后缀形式解析到清单里的 Opus 5.5。上游写法若不满足这两条，在上游写法上补。
- Osuna 测试里断言 Opus 5.5 默认思考档位为「高」的那一条改为「中」。这是第一段里唯一一处改动 Osuna 既有断言结论的地方，PR 正文写明（第二段还有一处，见「问题卡片」）。落到文件里是同一条参数化用例的两行参数（不带与带日期后缀的模型 ID 各一行）。日期后缀样例与用例标题的差异取上游的，两边独有的用例都留。
- 上游的归一化写法直接满足 `us.anthropic.` 前缀的两条断言，没有在上游写法上补代码；模型清单文件与上游逐字节相同。这两条断言在测试里单独成一条用例，不并进上游的用例。

**问题卡片（第二段）。** 以 Osuna 的卡片为底：

- 外观（编号行列表）与单选题「点击即作答」保持不变。
- 上游的多选修复移植进来：多选题里先勾选项再填「其他」、或先填「其他」再勾选项，两者都保留；提交内容为勾选项的标签在前、「其他」文本在后，以 `, ` 连接。
- 上游对卡片纯逻辑模块及其测试的改动已自动合并，照收。
- Osuna 的卡片把作答状态放在纯逻辑模块里，上游的修复改的是组件里的状态处理。组件的冲突块整块取 Osuna 的，上游的行为改在纯逻辑模块的两个状态函数上：多选题勾选项不再清掉「其他」的文字，输入「其他」不再清掉勾选项；单选题仍互相替换。多选题里勾选项也不再收起已点开的「其他」输入行。
- Osuna 原有的用例 `typed other text and preset options replace each other` 用一道多选题断言「选项与『其他』互相替换」，与上一条相反。维护者 2026-10-10 确认按上一条走：该用例改用单选题断言互相替换，另加一条多选题「两者都保留」的用例。这是本次第二处改动 Osuna 既有断言结论的地方，PR 正文写明。
- 上游为卡片新增的浏览器测试照收。其中多选的两条用例必须在 Osuna 的卡片上通过：用例正文不改，测试的辅助函数 `type` 加一步——输入框还没出现就先点开「其他...」行（维护者 2026-10-10 确认）。单选的两条以「有提交按钮」为前提，与 Osuna「点击即作答」的决定矛盾之处按 Osuna 的行为改写用例，改写后仍要覆盖「单选题里选项与『其他』互相替换」这一结论，并在 PR 正文写明是哪条决定。

其余四个代码冲突文件按规则 3 两边都保留，不需要维护者裁决：

- 智能体管理：上游把刷新时的历史事件改为先收集再统一处理，并把会话配置准备的参数改成选项对象。Osuna 在同一处有两件事要落进上游的新流程：历史事件入时间线前去掉末尾的 Routing block；会话配置准备多返回的 Paseo 工具门控原因。
- Claude 会话及其测试：只有 import 块冲突，两边的引用都留。

### 版本号与发版元数据

按 `docs/release.md`「版本号与发版元数据」的表处理。本次的具体情况：

- 所有工作区的版本号保持 `0.14.2`。上游在这两段里没有改外部依赖，解完的各 `package.json` 除 `packages/server/package.json` 多出上游的一个脚本（`analyze:observer-metrics`）外与合并前相同；`package-lock.json` 重新生成后与合并前逐字节相同，以此自检。
- `CHANGELOG.md` 只保留 Osuna 的条目，不搬上游的 0.9.1、0.9.2 条目。
- 四个 README 的冲突块取 Osuna 的。
- `.gitignore` 两边各加了一条，都留。
- 上游新增的八个安卓商店说明文件与 Osuna 已有文件不重名，照收。

### 上游没有触及、合并后仍要核对的不变量

模拟合并显示上游在这两段里没有改协议消息、没有新增 `COMPAT(...)` 标签、没有改翻译资源、没有在应用与 CLI 源码里新增上游站点链接、没有改桌面打包与发版工作流。`docs/release.md`「合并后核对」的各项仍在每段合完后逐项过一遍，预期全部无变化；任何一项有变化都先查清原因再继续。

上游在应用界面里新带来的用户可见英文若出现在设置界面，改走翻译键，九种语言齐全。

- 上游在 CI 里新增的 macOS 文件观察测试作业照收。
- 上游对官网赞助页的改版只落在官网包里，照收。官网在本仓库只手动部署，应用内不出现赞助入口。

- `docs/release.md`「从上游同步」里写明当前同步点的那一句更新为 v0.9.2 及其提交，本次两段的 merge commit 与 PR 编号补在旁边。
- 本次新踩到的、下次还会遇到的坑补进「踩过的坑」；没有就不加。不为这次合并另写流水账。

## UI and Design

这次不引入新的视觉方向，也不新增界面。唯一涉及界面的是问题卡片：外观保持 Osuna 现有的样子，只改多选题的作答行为。`.atw/spec/app/frontend/` 的组件与质量规则适用。

目标视口：Electron 桌面端 1280 宽。原生端免验收。

截图可核对的验收点：

- 多选问题卡片仍是编号行列表；勾选两个选项并在「其他」里填了文字后，勾选状态与「其他」里的文字同时可见。
- 该问题提交后，聊天里显示的回答同时含勾选项与「其他」的文字。
- 单选问题卡片点击某个选项即完成作答，不出现额外的提交步骤。
- Claude 模型列表里有 Opus 5.5；新建一个未手动选过档位的 Opus 5.5 对话，思考档位显示「中」，档位列表里没有关闭思考。
- 刷新一个已有多轮对话的智能体后，时间线里没有重复的消息，历史消息末尾没有 Routing block。

## Testing Decisions

好的测试只断言外部行为：给定输入与状态，用户或调用方看到什么。这次是合并，测试的作用是证明两边的行为都还在，因此只用已有的测试和上游随合并带来的测试，不新开接缝。

### 接缝

1. **CI 全套作业**（最高接缝）。format、lint、typecheck、server-tests、desktop-tests、app-tests、sdk-tests、playwright 分片、relay-tests、cli-tests，加上游新增的 macOS 文件观察作业。上游为这 62 个提交带来的测试随合并进入这些作业，Osuna 的测试守住 Osuna 的功能。
2. **冲突文件对应的现有测试**，本机逐个文件跑：
   - Claude 模型清单的测试：Opus 5.5 的清单条目、默认档位「中」、前缀与日期后缀的解析。
   - Claude 会话的测试，以及上游新增的回退锚点测试。
   - 智能体管理的测试与 Routing block 的现有测试（去尾逻辑的单元测试、提及路由的 daemon e2e）：刷新后时间线不重复、Routing block 不进历史。
   - 问题卡片纯逻辑模块的测试，以及上游新增的卡片浏览器测试。
3. **Osuna 不变量的现有测试**。桌面更新源的测试、翻译资源测试。
4. **dev 桌面端实测**。见验收清单。
