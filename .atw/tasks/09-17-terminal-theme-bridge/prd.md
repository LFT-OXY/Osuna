# 终端主题桥与对称留白：让 TUI 拿到真实前景/背景色

**Status:** ready-for-agent
研究依据：`research/terminal-vs-orca.md`（含根因定位、orca 做法、接口事实）。

## Problem Statement

在 macOS desktop 上，用户用浅色主题打开一个终端并启动 Codex、Pi 等 TUI 时，TUI 按深色终端渲染：Codex 的输入框是一块纯黑底，文字看不见；Pi 的提示文字发白、对比度极低。切换 app 主题后，已经运行的 TUI 也不会跟着变。

原因是 daemon 代替客户端回答终端程序的颜色查询时，前景/背景色是写死的深色值，客户端的真实主题从未到达 daemon。

另外两个独立的观感问题：终端内容左侧贴着面板边缘、右侧却留有空白，视觉不对称；终端关闭了 xterm 的自动对比度修正，浅色调色板里的 ANSI white 与白底同色，导致部分输出不可见。

## Solution

客户端把自己终端的前景、背景、光标颜色推送给 daemon。daemon 用这些真实值回答 TUI 的颜色查询（OSC 10/11/12）和深浅色方案查询（`CSI ?996n`），并在 TUI 订阅主题变更（`DECSET 2031`）后，于 app 切换深浅主题时主动通知它（`CSI ?997n`）。没收到客户端颜色之前，daemon 对这些查询保持沉默，不再伪造默认值。

同一个终端被多个客户端打开时，颜色跟随已有的"终端尺寸所有者"，不新增仲裁规则。

终端宿主四周加相同的内边距；xterm 最小对比度按背景亮度取值；修正浅色调色板中与背景同色的 ANSI 颜色。

## User Stories

1. 作为使用浅色主题的 desktop 用户，我希望在终端里启动 Codex 时输入框按浅色方案渲染，这样我能看清自己输入的内容。
2. 作为使用浅色主题的 desktop 用户，我希望 Pi、Claude Code 等 TUI 的文字颜色与白底有足够对比，这样我不用眯着眼读警告信息。
3. 作为使用深色主题的用户，我希望现有深色体验保持不变，这样这次修复不会把我的终端变浅。
4. 作为用户，我希望在 app 里从浅色切到深色（或反过来）后，已经在运行的 TUI 立刻跟着切换配色，这样我不用重启 agent。
5. 作为用户，我希望通过 Terminal profile 启动的 agent 在第一帧就拿到正确的颜色，这样不会出现"先黑后白"的闪动。
6. 作为同时用 Mac 和手机打开同一个终端的用户，我希望 TUI 的配色跟随当前正在操作它的那台设备，这样我在 Mac 上打字时看到的是 Mac 主题下的样子。
7. 作为用户，我希望终端内容左右两侧的留白一致，这样多分栏时视觉对齐。
8. 作为用户，我希望终端内容不再贴着面板边缘，这样第一列字符不会被边框吃掉。
9. 作为浅色主题用户，我希望用 ANSI white 输出的文字在白底上仍然可读，这样 `ls` 之类命令的输出不会消失。
10. 作为用户，我希望终端对暗色背景上接近背景色的文字做温和提亮，但不把鲜艳的颜色洗白，这样深色主题下的语法高亮不失真。
11. 作为连接到旧版本 daemon 的用户，我希望新版客户端不会因为发送 daemon 不认识的消息而断开终端，这样升级客户端不影响老 host。
12. 作为连接新版 daemon 的旧版客户端用户，我希望终端行为与以前一致，这样我可以晚点再升级客户端。
13. 作为通过浏览器（非 Electron）使用 web 版的用户，我希望同样享受到正确的颜色应答和对称留白，这样两种 web 形态表现一致。
14. 作为维护者，我希望颜色应答逻辑有真实 PTY 级别的测试覆盖，这样以后改 daemon 终端管道时不会悄悄回退到写死的黑色。

## Implementation Decisions

### 客户端到 daemon 的视图属性

- 新增一种终端客户端消息类型"视图属性"，字段为前景色、背景色、光标色，均为 `#rrggbb` 格式；与 resize 走同一条终端输入通道，沿现有 worker 转发路径直达终端会话，不新增 worker 协议类型。
- `create_terminal_request` 增加同结构的可选字段。创建终端的客户端在创建时就带上颜色，daemon 在 PTY 启动前就持有它，避免 TUI 启动时的查询与订阅之间的竞态。
- 新字段一律可选，wire schema 保持纯 zod 对象，不用 transform/catch/preprocess。生成的入站校验需同步重新生成。
- daemon 在 `server_info.features` 增加一个能力位，客户端只在能力位为真时发送视图属性消息；不为真则不发，不做任何回退路径。这条为老 daemon 服务，需按 COMPAT 约定打标签并写移除日期。

### 所有权

- 视图属性更新消息只接受来自当前"终端尺寸所有者"连接的消息，其余连接的消息静默忽略，与 resize 的 update 语义一致。
- 客户端在每次发送 `claim` 意图的 resize 之后紧接着发送一次视图属性，并在自身主题变化时再发。这样焦点切换到另一台设备时，颜色随所有权一起转移。
- 创建请求里的初始颜色不需要所有权（此时还没有所有者）。

### daemon 应答

- daemon 侧 headless 终端保存最近一次收到的视图属性；未收到过时为空。
- 空时对 OSC 10/11/12 的 `?` 查询和 `CSI ?996n` 一律消费但不回复；不再写死默认色。现有回复的字节格式（ST 结尾、16 位通道复写）保持不变。
- `CSI ?996n` 的深浅判定用背景与前景的相对亮度（WCAG 公式，与 xterm 一致）：背景更暗为深色（回复 `?997;1n`），否则浅色（`?997;2n`）。
- 解析 `DECSET 2031` 的开启/关闭，记录该会话是否订阅了主题变更。已订阅且新收到的视图属性使深浅判定翻转时（含从"未知"变为已知：终端创建时没有颜色、之后首次收到），主动向 PTY 写一次 `CSI ?997;1n` 或 `?997;2n`。未订阅的会话不主动写。
- 不处理 OSC 4 调色板查询，不实现 TUI 的 OSC SET 覆盖层与 104/110/111/112 恢复。
- 所有回复仍通过现有的"直接写入 PTY"路径，不经过 WebSocket 往返。

### 客户端

- 浏览器端 xterm 继续吞掉 OSC 10/11/12 查询，不改。
- 客户端把当前 xterm 主题里的前景、背景、光标色转成 `#rrggbb` 后发送；主题对象变化时重新发送，值相同则不重复发。
- 终端宿主四周使用同一个设计系统 spacing token 作为内边距，内边距区域用终端背景色填充；fit 按扣除内边距后的内框计算行列。不做用户设置项。
- xterm 最小对比度按当前主题背景亮度取值：浅底 4.5，深底 3。仅在值变化时写入，避免无谓清空 xterm 的对比度缓存。
- 浅色调色板中 `white` 与 `brightWhite` 改为在白底上可读的灰色，其它 ANSI 色不动。
- 原生（iOS/Android）终端渲染文件不在本次修改范围，但共享的协议与 daemon 逻辑对它们同样生效。

## Testing Decisions

好的测试只观察外部行为：TUI 从 stdin 收到了什么字节、xterm 暴露了什么选项、DOM 里内框与外框的几何关系。不断言内部缓存或私有字段。

测试缝隙从高到低：

1. **daemon 真实 PTY 缝隙**（首选，已有先例）：server 包终端 POSIX 测试套件里已有一个"前台程序查询 OSC 11 并从 stdin 收到回复"的用例，用一个 node helper 脚本作为前台程序。沿同一缝隙增加：带视图属性创建终端时 helper 收到对应的 rgb 回复；不带时 helper 超时（沉默）；`?996n` 按亮度回复；helper 先开启 2031，随后更新视图属性使深浅翻转，helper 收到 `?997n`；翻转不发生时不收到。
2. **worker 转发缝隙**：worker 终端管理器测试里加一例，确认视图属性消息穿过 worker 到达会话。
3. **所有权缝隙**：终端会话控制器测试已用假会话和会话投递验证 resize 的所有权，增加视图属性的同类用例：非所有者被忽略、所有者生效、`claim` 后新所有者生效。
4. **协议缝隙**：protocol 包的 schema 测试增加新字段/新消息的解析用例，并覆盖"老消息不带新字段仍可解析"。
5. **客户端浏览器缝隙**：app 包已有的 emulator runtime `*.browser.test` 里增加：浅色主题挂载后最小对比度为 4.5、深色为 3、切主题后只在变化时写入；宿主内框相对外框四边等距。流控制器的单元测试增加：attach 时 `claim` 之后紧接视图属性；主题变化时再发；能力位为假时不发。
6. 不新增 Playwright 用例；不新增 e2e 套件。

先例：server `terminal.posix.test.ts` 的 OSC 11 helper 用例；`terminal-size-ownership.test.ts` 与 `terminal-session-controller.test.ts` 的所有权用例；app `terminal-emulator-runtime.browser.test.ts` 的挂载与主题用例；`terminal-stream-controller.test.ts` 的 attach 序列用例。

## Out of Scope

- OSC 4 调色板查询、TUI 的 OSC SET 覆盖层与 104/110/111/112 恢复。
- 独立的终端主题选择器、主题预设、外部调色板导入。
- 内边距设置项。
- 手机端（iOS/Android）原生终端渲染与 WebView 终端的内边距和对比度。
- 输入延迟、resize 抖动、滚动、复制粘贴、快捷键。
- 默认 shell 以登录 shell 方式启动、shell 选择、Terminal profile 的数据模型。
- 手机端与 desktop 主题不一致时的任何"合并"策略：只跟随尺寸所有者。

## Further Notes

- orca 把同一问题命名为"默认黑 OSC-11 bug"，其三条不变量本方案照搬：未知即沉默；深浅判定用相对亮度而非 app 模式；TUI 自己改过的颜色由主题重推整体覆盖（本次不实现覆盖层，因而第三条暂无影响）。
- 视图属性是 app 级快照而非每终端配置：所有终端共享一套主题，但所有权是每终端的，所以消息仍按终端发送。
- 深浅翻转通知只在分类变化时发，避免主题微调（同为浅色的两套配色）触发 TUI 全量重绘。"未知→已知"也算分类变化：老客户端或 CLI 创建的终端里 TUI 查询时只得到沉默，新客户端 claim 后推送颜色，这一次通知让它拿到正确配色。
- 客户端能力位门控落在 `DaemonClient.sendTerminalViewAttributes`（与工单 01 的创建请求门控同层、同一个能力位），流控制器只负责"claim 后紧接推送、主题变化去重推送"。工单 01 与 02 共用 `terminalViewAttributes` 能力位，必须随同一个版本发布。
- 验证方式：按 `docs/testing.md`，只跑改动到的测试文件；改动 protocol 后先 `npm run build:client`，改动 server 后 `npm run build:server`；每次改动后 `npm run typecheck` 与 `npm run lint`。人工验收在 macOS desktop 浅色主题下启动 Codex 与 Pi 各一次，切换到深色再切回，观察输入框与提示文字。

## Acceptance Criteria

- [ ] 浅色主题下通过 Terminal profile 启动 Codex，输入框为浅色底、文字可读；Pi 的提示文字对比度正常。
- [ ] 深色主题下上述 TUI 表现与修改前一致。
- [ ] 运行中的 TUI 在 app 切换深浅主题后跟随切换（以 Codex 为验证对象）。
- [ ] 老客户端连接新 daemon：终端功能不变，daemon 对颜色查询沉默。
- [ ] 新客户端连接老 daemon：不发送视图属性，终端不断开。
- [ ] 终端内容四周留白相等；多分栏时左右边缘对齐。
- [ ] 浅色主题下 ANSI white 与 brightWhite 输出可读。
- [ ] Testing Decisions 列出的六类测试缝隙中第 1 至 5 项各有新增用例且通过。
- [ ] `npm run typecheck`、`npm run lint` 通过；入站校验代码已重新生成。
