# 改前基线（工单 02，2026-10-19）

结论先说：固定场景里**没有复现窗口冻住**，慢在「等 daemon 算完」。三条合格标准里，「打开面板 ≤2 秒」靠第一期的做法达不到，本工单按停下条件结束，等用户决定（见末节）。

## 测量环境

- 机器：Apple M3 Max，16 核，64GB 内存，macOS 26.4；Node 24.15.0。
- 代码：`5386e4d0a`（已含工单 01 摘入的 #6745）加本工单的测量代码，产品代码未改。
- 三处测量，都是开发构建，没有用打包版：
  - **daemon**：vitest 里起进程内 daemon（`git-diff-bottleneck.local.e2e.test.ts`），git 子进程限速改回正式版默认的 64 个/秒、同时 8 个（vitest 配置默认放宽到 10000/秒，不改回来数字会偏好看）。不替换任何函数：订阅推送按到达时间记；单次刷新耗时是订阅释放后直接调 daemon 刷新时用的同一个 `getCheckoutDiff` 量的；高亮耗时是按 daemon 的做法给每个文件的新旧两版全文各调一次 `highlightCode` 量的。
  - **浏览器**：Playwright 无头 Chromium，Metro 开发包（React 开发模式），CPU 不降速，视口 1280×900。
  - **桌面版**：dev Electron 44.2.0（`npm run dev --workspace=@getpaseo/desktop`，daemon 跑 `packages/server/dist`，独立子进程），窗口内宽 1280×900，Playwright 经 CDP 接入。
- 开发构建比打包版慢（React 开发模式、未压缩），所以渲染进程的数字偏保守；daemon 的数字与打包版同一份代码。

## 场景

`packages/server/src/server/daemon-e2e/diff-perf-scenario.ts`，内容只由下标决定，两次生成的 `git diff` 逐字节相同（已核对 md5）。

- 200 个 `.ts` 已有文件，每个 2000 行，各改 50 行（5 段 × 10 行，additions + deletions = 100）；
- `.sql`、`.sh`、`.toml` 各 3 个，规格同上；
- 50 个新建文件，每个 200 行；
- `package-lock.json` 改动 30,000 行（patch 1.4MB，超过单文件 1MB 上限，显示为 `too_large`）；
- 合计 260 个文件、patch 约 2.7MB；lock 文件以外约 1.7MB，没碰到 2MB 总量上限，50 个新文件都在结果里；
- 模拟 Agent：每 0.5 秒轮流改一个 `.ts` 模块的一行，持续 60 秒，共 120 次。

### 渲染进程（打开面板）

「看到清单」= 点开 Changes 到文件树出现第一个文件；「看到内容」= 再点文件到 diff 画布出现。打开的 diff 面板默认全部展开，260 个文件都在同一个文档里，量的是整份列表，不是单个文件。

| 项 | 浏览器 | 桌面版 |
| --- | --- | --- |
| 看到清单 | 11.1 秒 | 7.7 秒 |
| 看到内容 | 11.4 秒 | 7.9 秒 |
| 打开期间长任务 | 5 次，最长 114ms | 4 次，最长 102ms |

### 卡顿时间花在哪

CPU 采样里连续忙碌 ≥50ms 的片段（与长任务同一阈值）合计约 1.7 秒（浏览器）/ 2.0 秒（桌面版），按段拆开：

| 段 | 浏览器 | 桌面版 |
| --- | --- | --- |
| 整包解析（`JSON.parse`） | 12.5% | 12.1% |
| 校验（`validateWSOutboundMessage`） | 7.9% | 7.7% |
| 垃圾回收（推测主要来自解析 16MB 消息） | 24.5% | 23.5% |
| `shareCheckoutDiff` 深比较 | 1.9% | 1.7% |
| 行模型重建（`buildDiffDocumentModel`） | 3.7% | 2.7% |
| 绘制（`paintWebViewport` 等） | 1.2% | 1.4% |
| React 其余渲染与提交 | 22.5% | 18.3% |
| 浏览器自身（样式、布局、合成） | 14.5% | 16.9% |
| 其他 JS（含消息分发） | 11.3% | 15.8% |

解析、校验和它带来的垃圾回收合计约 45%，深比较、行模型、绘制合计不到 7%。但单个长任务最长只有 100–170ms；渲染端没有记推送次数，按 daemon 侧同一场景 1 分钟推 7 次估算，主线程大部分时间是空的。

这台机器是 M3 Max、CPU 不降速；更慢的机器上同样的工作会按比例变长。按单个长任务最长约 170ms 算，CPU 慢 3 倍以上才会碰到 0.5 秒，没有实测。

## 对照合格标准

| 标准 | 改前 | 判断 |
| --- | --- | --- |
| 打开面板 ≤2 秒看到内容 | 桌面版 7.9 秒 | **需要用户重新决定**（见下） |
| 1 分钟内没有一次长任务超过 0.5 秒 | 最长 102ms（桌面版）/ 153ms（浏览器） | **可达**：改前已满足。固定场景没有复现「窗口冻住」 |
| daemon 每次刷新耗时 ≤ 改前 1/5（≤1.8 秒） | 中位 9.0 秒 | **可能可达**：高亮占 84%，按文件复用后只需高亮变了的那个文件（约 30ms）；但 git 那段实测 1.1 秒，复用后如果每次仍要跑这些 git 命令，加上读全文与拼装，约 1.2–1.5 秒，余量不大，要实测确认 |

为什么「打开 ≤2 秒」靠第一期做不到：打开时 daemon 是冷的，按文件复用（工单 05）没有可复用的东西；默认收起（工单 06）只少画几行，daemon 照样给所有文件读全文、做高亮；只要清单的订阅（工单 08）能让文件树很快出来（只跑 git 那段实测 1.1 秒），但点开正文时仍要等完整计算，约 9 秒。要让正文 2 秒内出来，得只给展开的文件算高亮，也就是第二期的「按文件取内容」。

## 停下：需要用户决定的事

1. **「打开 ≤2 秒」怎么算。** 可选：
   - 改为「≤2 秒看到文件清单」——工单 08 做完后可能可达，正文仍要约 9 秒；
   - 保留「≤2 秒看到正文」——要把第二期（只算展开文件的内容）提前；
   - 放宽数字（例如正文 ≤10 秒）——第一期做法下可达，但用户等的时间基本不变。
2. **「窗口冻住」在这个场景里没出现。** 用户实际遇到的冻住可能来自比这个场景更大的改动（文件更多、单个推送更接近 23MB 上限），也可能感受到的「卡」其实是每次都要等 8–9 秒的刷新。要不要换一个能复现冻住的场景（比如用户实际的仓库规模），再决定工单 04、09 的优先级。

## 工单 09 桌面版实测：最小化时释放订阅（2026-10-19）

代码 `09af62627`（`useCheckoutDiffQuery` 的订阅条件多了 `useAppVisible()`：页面 hidden 时和 tab 不活跃一样释放；只看 hidden，不看失焦）。dev Electron 44.2.0，daemon 跑 `packages/server/dist`（6769），工单 02 的场景，Changes 面板开着文件树并点开一个文件（同时有清单订阅和完整订阅）。最小化和还原用 System Events 设 `AXMinimized`；模拟 Agent 每 0.5 秒改一个文件，持续 110 秒，最小化前 15 秒就开始改。daemon 侧看 `daemon.log` 每 30 秒一条的 `ws_runtime_metrics` 和 `ws_slow_request`。
