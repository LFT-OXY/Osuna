# Diff 面板在改动文件多时卡顿（第一期）

访谈 Q1–Q17 于 2026-10-19 由用户逐题回答，全部决定见 [`research/decisions.md`](research/decisions.md)；Osuna 现状见 [`research/osuna-current.md`](research/osuna-current.md)，参考项目做法见 [`research/reference-projects.md`](research/reference-projects.md)。卡顿来自上游原有设计，Osuna 自己的改动未见性能退化（对比过程见 decisions.md 末节）。

## Problem Statement

用户在桌面版 Osuna 的 **Changes** 面板里看改动。改动的文件一多，面板就卡：打开时等很久，滚动和点开文件时卡顿，Agent 一边改文件、面板一边跟着刷新时越来越卡，严重时整个窗口没有反应。

读代码确认的原因：

1. 任何一个文件变了（等 150ms），daemon 就把**所有**改动文件从头算一遍：重取 patch、读新旧两版全文、对两版整文件做语法高亮，再整包推给客户端。Agent 持续改文件时，就是一遍接一遍的全量重算。
2. 未跟踪的新文件一个一个串行处理，每个文件起一个 git 子进程。
3. 每次推送都是整包，每行文字在包里存两份，最大可到十几 MB。客户端主线程每次都要整包解析、校验、和上一份深比较、重建行模型。窗口冻住最可能出在这一步（推测，第一步实测确认）。桌面版 daemon 是独立子进程，它再忙也不会直接冻住窗口。
4. 只看文件树也照样收到完整的高亮内容。
5. 窗口最小化时客户端不退订，照样接收、照样处理。
6. 所有文件默认展开，包括几万行的 lock 文件。
7. Bug：改动总量超过 2MB 以后，剩下的未跟踪文件直接从列表里消失，连「太大」的占位都没有。

## Solution

做完以后，用户看到的是：

- 改动只有几个文件时，面板和现在一样：全部展开。超过 10 个文件时只展开前 3 个，其余收起，点文件头就能展开。
- **Generated file**（lock 文件、`.gitattributes` 标了 `linguist-generated` 的文件、压缩过的 `*.min.js` / `*.min.css` / `*.map`）不论多少都默认收起，文件名旁标「生成」。改动超过 1000 行的文件也默认收起，标「改动 1,234 行」。
- 已经显示在眼前的文件不会因为别的文件出现而突然收起。手动展开或收起过的文件照旧记住。「全部展开」真的全部展开。
- Agent 狂改文件时，面板最多每秒更新一次；改动一停，最后一次的结果马上补上。窗口不再冻住。
- 只开文件树时，面板只拿文件清单，不拿内容。
- 窗口最小化时不再接收改动；恢复时补拿一次最新的。
- 超过 2MB 以后的新文件照样出现在列表里，显示「太大」。

在下面的固定测试场景里，打开面板 2 秒内看到内容；Agent 持续改文件的 1 分钟里，桌面版窗口没有一次冻住超过 0.5 秒；daemon 每次刷新的耗时降到改前的五分之一以下。

## User Stories

1. 作为 Osuna 用户，我想在改动有几百个文件时打开 Changes 面板，2 秒内就看到内容，这样我不用干等。
2. 作为 Osuna 用户，我想在 Agent 持续改文件时，窗口始终能点、能滚，这样我能一边看 Agent 输出一边看改动。
3. 作为 Osuna 用户，我想让 Agent 狂改文件期间面板最多每秒更新一次，这样界面不会被一遍遍刷新拖住。
4. 作为 Osuna 用户，我想在 Agent 停下以后立刻看到最终的改动，这样我不会看到过时的内容。
5. 作为 Osuna 用户，我想在改动文件不超过 10 个时照旧全部展开，这样小改动的体验和以前一样。
6. 作为 Osuna 用户，我想在改动文件超过 10 个时只看到前 3 个展开，其余收起，这样面板打开就不重。
7. 作为 Osuna 用户，我想点一下收起文件的文件头就能展开它，这样我想看哪个看哪个。
8. 作为 Osuna 用户，我想让 lock 文件这类 Generated file 不管多少都默认收起，这样几万行自动生成的内容不会挡在我要看的代码前面。
9. 作为 Osuna 用户，我想让项目在 `.gitattributes` 里标成 `linguist-generated` 的文件也被当成 Generated file，这样项目自己的约定也生效，和 GitHub 网页一致。
10. 作为 Osuna 用户，我想让 `*.min.js`、`*.min.css`、`*.map` 默认收起，这样压缩代码不会占满屏幕。
11. 作为 Osuna 用户，我想在收起的 Generated file 旁看到「生成」标签，这样我知道它为什么被收起。
12. 作为 Osuna 用户，我想让改动超过 1000 行的文件默认收起，并标出改了多少行，这样我能决定要不要点开。
13. 作为 Osuna 用户，我想让因为文件太多而被收起的普通文件不加标签，这样它看起来和我手动收起的一样，不显得杂乱。
14. 作为 Osuna 用户，我想让已经显示在眼前的文件在 Agent 又新建文件后保持原样，这样我正在看的内容不会突然收起。
15. 作为 Osuna 用户，我想让新出现的文件按规则决定默认展开还是收起，这样文件越来越多时面板不会越来越重。
16. 作为 Osuna 用户，我想让我手动展开或收起过的文件一直保持我的选择，这样我的操作不会被默认规则覆盖。
17. 作为 Osuna 用户，我想点「全部展开」时连 Generated file 和大文件一起展开，这样按钮的意思和字面一致。
18. 作为 Osuna 用户，我想在只开文件树时，面板只拿文件清单，这样只看清单时也不卡。
19. 作为 Osuna 用户，我想在把窗口最小化时让面板停止接收改动，这样后台不白白占用电脑。
20. 作为 Osuna 用户，我想在窗口恢复时立刻看到最新的改动，这样暂停接收不会让我看到旧内容。
21. 作为 Osuna 用户，我想让超过 2MB 总量以后的新文件照样出现在列表里，并显示「太大」，这样我不会漏看 Agent 新建的文件。
22. 作为 Osuna 用户，我想在有几十个新建文件时面板也很快出来，这样新文件多不再意味着慢。
23. 作为 Osuna 用户，我想让只改了一个文件时，面板只为这个文件重新计算，这样刷新的快慢和改动总量无关。
24. 作为 Osuna 用户，我想让面板显示的内容和改前完全一致（同样的行、同样的颜色），这样提速不以显示出错为代价。
25. 作为 Osuna 用户，我想在连着还没升级的旧 daemon 时面板照常能用，这样更新顺序不会把面板弄坏。
26. 作为通过手机 Paseo 连到 Osuna daemon 的用户，我想让新 daemon 发来的消息照常解析，这样手机端不会因为这次改动出错。
27. 作为 Osuna 用户，我想先修好上游已修的「第一次改动后 Diff 不再更新」，这样提速的验证不被这个老问题干扰。
28. 作为维护 Osuna 的人，我想有一个固定的测试场景和一组前后对比的数字，这样我能确认提速是真的，以后也能复测。
29. 作为维护 Osuna 的人，我想先实测卡在哪一步再动手，这样如果卡点只有第二期能解决，我能提前知道并决定是否提前第二期。
30. 作为维护 Osuna 的人，我想让这次改动尽量不碰上游也会改的地方，这样以后合并上游时冲突少。

## Implementation Decisions

**顺序**

1. 摘取上游 be0acb293（#6745 keep Diff updates alive after the first edit）。只动客户端 push-router 和它的测试，加一个浏览器用例。
2. 建固定测试场景并测出基线（见 Testing Decisions），把数字写进 `research/baseline.md`。如果基线显示窗口冻住主要来自整包解析、深比较这类只有第二期能解决的部分，或者某条合格标准明显不现实，停下，带数据找用户，不自行放宽标准。
3. 后面的 daemon 改动和客户端改动互不依赖。

**daemon：按文件复用**

- 每个文件算出的 patch 和高亮结果按「这个文件的身份」缓存，后续刷新中身份没变就直接复用。身份由 compare 参数、路径、旧侧 blob、工作区一侧的文件签名组成。工作区一侧拿不到 blob hash，用 stat 签名（大小 + mtime + inode）代替。
- 文件监听已经拿得到变动路径，但现在丢在了 `notifyWorkingTreeChanged` 一层。这次改为把路径往下传，作为「哪些文件该失效」的提示。身份比对仍是兜底判断，所以收到不带路径的「有变化」信号（轮询降级、base 模式快照）时结果也正确，只是要多做几次 stat。
- 整份结果缓存的 key、去重指纹、推送消息的形状都不变。客户端看到的数据和改前逐字一致。
- 按文件缓存跟着现有的整份缓存一起淘汰，不单独设上限。cwd 不再被订阅时，它的按文件缓存一起释放。

**daemon：未跟踪文件并发**

- 未跟踪文件改成有上限的并发处理，走现有的 git 子进程限流，不另开池。结果仍按原来的顺序拼接，保证输出确定。

**daemon：刷新节奏**

- `CheckoutDiffManager` 现有的 150ms 防抖之外再加节流：连续有变动时，同一个 target 两次推送至少隔 1 秒；变动停下后，最后一次在 150ms 防抖后照常推出。现有的「正在算时又来变化就排队一次」保持不变。

**daemon：Bug 修复**

- 未跟踪文件在 patch 总量超过 2MB 后不再 `break`，剩下的文件改为输出 `status: "too_large"` 占位，和已跟踪文件超限时的做法一致。

**daemon + 协议：Generated file 识别**

- 由 daemon 判断，因为只有 daemon 读得到 `.gitattributes`。三条规则：一份 lock 文件名单（参考 orca 的 generated-code-path 名单）；`git check-attr linguist-generated` 为 true；路径匹配 `*.min.js` / `*.min.css` / `*.map`。
- 协议在 diff 的 file 结构上加可选字段 `generated?: boolean`。旧客户端忽略它；旧 daemon 不发，客户端就当作不是 Generated file。不加兼容兜底。
- `status` 枚举不加新值。旧客户端解析不了新的枚举值，会出错。

**协议：只要文件清单**

- `CheckoutDiffCompareSchema` 加可选字段，表示「只要文件清单」。打开时 daemon 返回的每个 file 仍带 path、oldPath、isNew、isDeleted、additions、deletions、status、generated，`hunks` 为空数组，并且跳过读全文和高亮。这个字段进入 `normalizeCompare` 和 target key，所以清单订阅和完整订阅各算各的、各自缓存。
- 在 `server_info.features` 加一个开关，宣告支持这个选项，并按项目规矩打 `COMPAT(...)` 标记。客户端只在开关为 true 时用清单订阅；连旧 daemon 时照旧走完整订阅。
- Changes 面板只开文件树、diff 正文不可见时，用清单订阅。正文一出现，就切换到完整订阅。

**客户端：减负**

- 窗口隐藏时释放 diff 订阅（桌面版最小化会让页面进入 hidden 状态），恢复可见时重新订阅，拿到一次最新快照。和现有的「tab 不活跃就退订」走同一条路径。
- 客户端收到推送后，最多每秒处理一次（用最后一份），并保留结尾那一次。daemon 已经节流，这一层是为连旧 daemon 时也能生效。
- 第二期之前，不改整包解析、`shareCheckoutDiff` 深比较和行模型重建的做法。

**客户端：默认展开规则**

- 规则作为一个纯函数，按以下顺序判断：
  1. 用户手动选过，按用户的选择；
  2. Generated file，收起；
  3. additions + deletions > 1000，收起；
  4. 本 tab 第一次看到这个文件时，改动文件总数 ≤ 10，展开；
  5. 总数 > 10 时，按面板里的显示顺序，前 3 个展开，其余收起。
- 「默认状态只在第一次见到时决定」要求 tab 状态记住「已经决定过的文件」。现有 `collapsedFilePaths` 只记得收起的文件，所以需要扩展 Changes 的 tab 状态，同时记下用户主动展开过的文件。持久化 schema 是 strictObject，新字段设为可选。
- 「全部展开」清空所有收起，包括 Generated file 和大文件；「全部收起」不变。

## UI and Design

- 视觉方向不变，沿用 Osuna 现有的 diff 外观（文件头、色条、分隔行）。只在收起文件的文件头上加一个灰色小标签，样式参照文件头里现有的次要文字（增删行数）。按 `.atw/spec/app/frontend` 的设计规范来，不另起新样式。
- 标签文案（中英都走 i18n）：
  - Generated file：「生成」/ "Generated"；
  - 大文件：「改动 1,234 行」/ "1,234 lines changed"，数字带千分位；
  - 因文件多而收起：不加标签。
- 需要有的状态：
  - ≤10 个文件全部展开；
  - >10 个文件只展开前 3 个；
  - Generated file 收起并带「生成」标签；
  - 大文件收起并带行数标签；
  - 超过 2MB 后的新文件显示现有的「太大」占位；
  - 只开文件树；
  - 窗口恢复后显示最新内容。
- 目标视口：桌面版 Electron 窗口，宽 1280；Web 同一套界面一并覆盖。原生端不做实机验收。
- 截图上可以核对的验收点：
  - 15 个文件的改动：第 1–3 个文件头下面有正文，第 4–15 个只有文件头；
  - 改动里有 `package-lock.json`：它的文件头带「生成」标签，下面没有正文；
  - 一个改了 1,500 行的文件：文件头带「改动 1,500 行」，下面没有正文；
  - 点「全部展开」后，上面这些文件都有正文；
  - 英文界面下，标签分别是 "Generated" 和 "1,500 lines changed"。

## Testing Decisions

好的测试只看外部行为：daemon 推出了什么、什么时候推；面板显示什么。不断言内部缓存怎么组织、调用了几次某个函数。用真实 git 仓库和真实文件，不 mock git。

**测试接缝**（优先用现有的）：

1. **daemon 的 checkout diff 订阅**：现有 `checkout-diff-manager.test.ts` 和 `checkout-git.test.ts` 的写法，在临时目录建真实 git 仓库。覆盖：
   - 改一个文件后推出的结果，和从零全量计算的结果逐字相同（按文件复用的正确性）；
   - 连续变动时推送间隔 ≥1 秒，停下后结尾那次推出（fake timers）；
   - 2MB 之后的未跟踪文件出现在结果里，`status` 为 `too_large`；
   - 三类 Generated file 被标出 `generated: true`，普通文件不标；
   - 只要文件清单时，`hunks` 为空，清单字段齐全；
   - 多个未跟踪文件并发处理后，结果顺序和串行时一致。
2. **Changes 面板的默认展开规则和 tab 状态**：纯函数单测，放进现有的 `panels/changes/state.test.ts` 或 diff-document 的 `model.test.ts` 旁边。覆盖 User Stories 5–17 的每条规则，包括「中途越过 10 个时已显示过的文件不变」。
3. **客户端订阅**：现有 `push-router.test.ts`。覆盖：页面隐藏时释放订阅、恢复时重新订阅；推送合并到每秒最多处理一次并保留结尾；有 feature 开关时用清单订阅、没有时用完整订阅。

**性能场景**（改前改后各测一次，数字写进 `research/baseline.md`）：

- 固定场景：200 个已有文件，每个约 2000 行、各改约 50 行；50 个新建文件；一个改动约 3 万行的 lock 文件；另有若干 `.sql`、`.sh`、`.toml` 文件，用来顺带量这几类 StreamLanguage 高亮的开销。再用一个模拟 Agent 的脚本，每 0.5 秒改一个文件，持续 1 分钟。
- daemon 侧扩展现有的 `git-diff-bottleneck.local.e2e.test.ts`（环境变量门控），量每次刷新的耗时。浏览器侧扩展现有的 `diff-performance.spec.ts` 和它的 baseline 文件（`PASEO_DIFF_PERF_E2E=1` 门控），量打开耗时和长任务。
- 桌面版验收在 dev Electron 里做，按已有的 Playwright CDP 做法，用 PerformanceObserver 记录 longtask，量单次冻住时长。
- 合格标准：
  - 打开面板 ≤2 秒看到内容；
  - 1 分钟内没有一次长任务超过 0.5 秒；
  - daemon 每次刷新的耗时 ≤ 改前的 1/5；
  - 2MB 新文件消失的 bug 有用例证明已修。
- 性能用例不进默认 CI，保持现有的环境变量门控，不新建 npm 脚本。
